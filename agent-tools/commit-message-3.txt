Populate customer-attested disk bindings for the three real LIMS DEV v2 data disks; exact resource-ID fix; documentation corrections

Starting from commit 16ffb9b (which proposed the customer-attested
guest-disk-UniqueId binding mechanism disabled by default), this change
populates it with reviewed, customer-supplied evidence for all three real
disks, fixes a managed-disk resource-ID matching gap, corrects several
over-claiming statements in comments/docs, and extends end-to-end test
coverage accordingly.

1) Populated bindings (Get-ApprovedDiskPreparationAllowlist), from
   customer-supplied, read-only Azure/guest inventory evidence
   (subscription 8ebb26a1-674a-40d1-97f8-e0a237e288a6, resource group
   rg-compute-lims-dev-westeu):
   - APP (vm-lims-dev-v2-westeu-001, appdata-vm-lims-dev-v2-westeu-001,
     LUN 0): AttestedGuestUniqueId = 60022480D1B07E6ACD98417F86591F4B
     (observed guest capacity 137436250112 bytes).
   - SQL DATA (vm-lims-dev-v2-westeu-002, sqldata-vm-lims-dev-v2-westeu-002,
     LUN 0): AttestedGuestUniqueId = 60022480FC5A2FF57B5FE802967E448E
     (observed 1099506078720 bytes).
   - SQL LOG (same VM, sqllog-vm-lims-dev-v2-westeu-002, LUN 1):
     AttestedGuestUniqueId = 60022480042D640894BBE41BA513DCFC (observed
     549753039360 bytes) -- this is the disk whose guest SCSILogicalUnit
     collides with the temporary disk; the attested UniqueId is what
     disambiguates it.
   Both App and Sql are now in full, complete, mutually unique attested
   mode (Test-AttestedGuestUniqueIdBindingConfiguration.IsAttestedMode=
   $true for each). These values are documented as a reviewed,
   customer-supplied diagnostic observation -- never independently
   re-verified by this script, never cryptographic/platform-asserted
   proof of the Azure-disk-to-guest-disk relationship (Azure exposes no
   such mechanism), and never automatically discovered or refreshed; a
   disk replacement/recreation/UniqueId change blocks and requires a new,
   separately reviewed binding. Populating these bindings changes only
   disk IDENTIFICATION -- it does not enable or authorize Apply or any
   mutation, which remain gated entirely by -Mode Apply plus the module's
   own independent enableGuestDiskPreparation/guestDiskPreparationExecutionTarget
   opt-ins (both still committed as false/'None').

2) Fixed an exact managed-disk resource-ID matching gap in
   Resolve-ApprovedDiskTarget: replaced a StartsWith(prefix) +
   EndsWith(diskName) check with a single, full, case-insensitive string
   equality against one fully-constructed expected resource ID. The
   previous combination could wrongly accept an ID containing an
   unexpected intervening path segment between the resource-group/
   provider prefix and the trailing disk-name segment (e.g.
   ".../disks/unexpected-segment/appdata-vm-lims-dev-v2-westeu-001")
   that is not the real disk's resource ID.
