Strip leading BOM and validate root element in Blob listing XML parsing

The live stage-only run received a Blob listing XML page and failed
converting it to System.Xml.XmlDocument. The failed [xml] cast's own
PSInvalidCastException embeds the entire input value being cast --
i.e. the full raw response body -- into its Message, which then
reached the pipeline log verbatim via Assert-LimsSqlMediaStagingFailure
and Write-Error.

Root cause: a UTF-8 BOM (U+FEFF) survives as a literal leading
character once the response body is decoded to a .NET string -- at
that point it is ordinary string content, not an encoding marker a
byte-stream-based parser would silently consume, so .NET's XML parser
rejects it as invalid content at the root level.

Fix in ConvertFrom-BlobListingXml (operations/compute/lims-ws2025-dev-
sql-media-staging/Stage-LimsSqlInstallationMedia.ps1):
- Strip a leading U+FEFF from the response string before parsing, the
  same way the diagnostic used while investigating the live failure
  stripped it.
- Parse via XmlDocument.LoadXml() directly instead of the [xml] cast
  operator, specifically to avoid PSInvalidCastException's raw-body-
  embedding Message. A failed LoadXml() call is wrapped by PowerShell
  in a MethodInvocationException (any direct .NET method call gets
  this treatment); its InnerException is the real XmlException, which
  is unwrapped to report a short diagnostic -- exception type, and
  LineNumber/LinePosition when the parser provides them -- without
  ever interpolating any exception Message or the response body
  itself into the failure message that reaches the pipeline log.
- Explicitly validate the parsed document's root element is
  'EnumerationResults'; a well-formed-but-wrong-shaped response (e.g.
  an Azure <Error> document) now fails closed with a clear message
  instead of silently matching zero blobs and an empty NextMarker.
- Pagination (NextMarker) is unchanged/preserved.

This failure path is reached only while building the staging plan,
before any destination directory is created or any file is written or
downloaded -- consistent with this script's existing "fail before any
write" design; nothing about that control flow needed to change.
