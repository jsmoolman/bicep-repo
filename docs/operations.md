### Cost Management Dashboard — lims

Built to the same repository pattern as the VM Availability SLA Dashboard v2. This workbook reads **exclusively** from the `CostManagementSnapshot_CL` Log Analytics table (see the LAW Ingestion Foundation and Snapshot Collector sections below) and does **not** call the Azure Cost Management REST API itself.

> **This is a refactor of an earlier, superseded implementation.** An earlier version of this workbook issued its own direct, interactive `Microsoft.CostManagement/query` REST call per selected Report Month; that implementation proved the query shape (see the collector proof below, which uses the same shape) but was never the intended production data path and has been fully removed from this workbook — no `Microsoft.CostManagement/query` reference, `queryType: 12`/ARMEndpoint query, or `CostDataJson` parameter exists anywhere in the current module. Git history preserves the previous direct-Cost-API implementation in full. **The LAW-backed workbook described below is implemented in code but has not yet been customer-side deployed, what-if'd, or validated** — see Outstanding work.

- **Reusable module:** [`modules/observability/cost-management-workbook/main.bicep`](../modules/observability/cost-management-workbook/main.bicep) — no LIMS-specific subscription IDs, management-group ID, or workspace ID; all are parameters. `workloadName` doubles as the `Project` value this workbook filters `CostManagementSnapshot_CL` by — there is deliberately no second, separate "project" parameter, so this value is never duplicated across two configuration points that could drift apart.
- **Reusable entrypoint:** [`src/observability/cost-management-workbook/main.bicep`](../src/observability/cost-management-workbook/main.bicep) — subscription-scoped orchestrator; workbook hosting (subscription/resource group/location) is configured independently from the Log Analytics workspace that hosts `CostManagementSnapshot_CL`.
- **LIMS configuration:** [`config/nfi/lims/observability/cost-management-workbook.bicepparam`](../config/nfi/lims/observability/cost-management-workbook.bicepparam) — reuses the existing LIMS reporting resource group/location and the existing central Log Analytics workspace (the same one the LAW Ingestion Foundation provisions `CostManagementSnapshot_CL` in). `managementGroupId` (the Tenant Root Group, `c7adbc6a-e0b3-4eb7-9403-ed7f7f48ec4b`) and `subscriptionEnvironmentMappings` remain declared in this file **unchanged** — see the compatibility note below.
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-cost-management-workbook.yml`](../.azuredevops/pipelines/deploy-cost-management-workbook.yml) — same commissioning posture as the VM Availability pipeline (`trigger: none`, `pr: none`, default `what-if`, explicit `deploy`). It has not been run from this repository.

**Compatibility note — `managementGroupId` and `subscriptionEnvironmentMappings` are intentionally still declared here:** the separate Cost Management Snapshot Collector script (see below) reads both values directly from this exact checked-in parameter file, by these exact parameter names, via `az bicep build-params` — that is the collector's own, unrelated, unchanged configuration contract and it is not restructured by this refactor. `managementGroupId` is no longer used by this workbook to query Azure Cost Management; it is retained here only because removing it would break the collector's `az bicep build-params` parse of this file, and it is still passed through to the module purely to preserve the workbook's existing deterministic resource name/GUID (see the module's own parameter description for the full reasoning). `subscriptionEnvironmentMappings`' `subscriptionId` values are similarly unused by the workbook now (`CostManagementSnapshot_CL` rows already carry their own `Environment` column, written by the collector) — the workbook only uses the distinct `environment` values, to build the Environment selector's choices and to zero-fill every configured environment in the grid.

**Design:**

- **Data source: `CostManagementSnapshot_CL` only.** Both grids query the Log Analytics workspace directly; there is no ARM/REST call, no hidden Cost Management parameter, and no externally-supplied JSON blob anywhere in this module.
- **Explicit, broad LAW query time context:** both grid queries set `timeContext.durationMs` to exactly 730 days (63,072,000,000 ms), matching `CostManagementSnapshot_CL`'s configured retention, so no workbook-level default time-range control can silently exclude an older, still-in-retention monthly snapshot.
- **Latest-whole-run selection (critical):** the collector's writes are append-only — repeated runs for the same `BillingMonth` create additional, complete snapshots rather than updating rows in place. For each `Project` + `BillingMonth`, the workbook selects the single newest `CollectionRunId` (by `max(TimeGenerated)` per run, then the most recent run per month) and uses **all** rows belonging to that one run — it never independently `arg_max()`s each Environment/Service row on its own, which could otherwise mix rows from two different collection runs for the same month. `TimeGenerated` is used only to rank collection runs by recency; all business/grid filtering uses `BillingMonth`.
- **Static, config-driven Environment domain:** identical mechanism to the VM Availability workbook's `subscriptionEnvironmentMappings` — repository configuration (its distinct `environment` values) is authoritative for the Environment selector's choices and for which environments the grid zero-fills, never a hard-coded literal list in the module.
- **Six-month window, calendar-accurate:** every grid shows the selected Report Month plus the five preceding calendar months, labelled with real `YYYY-MM` values. Report Month offers the current month plus the previous 12 completed calendar months.
- **Environment selection filters already-retrieved snapshot data only:** changing `Environment` never changes which `BillingMonth`/`CollectionRunId` rows are read from `CostManagementSnapshot_CL` — it only re-filters the result, exactly as the previous direct-Cost-API implementation guaranteed for its own single query.
- **Trend:** ordinary least-squares linear regression over the required trend months only (current partial month excluded when Report Month is current; all six months included when Report Month is historical). Classification applies a €10/month absolute noise floor first (below it, always `Stable`), then `Downward` (≤ -3%), `Stable` (-3%..+3%), `Mild Upward` (+3%..+10%), `Strong Upward` (≥ +10%) — thresholds, formula, labels, and colors are unchanged from the previous implementation.
- **Trend fails closed, new in this refactor:** if any month required for the trend calculation lacks a valid snapshot, the trend is not computed by treating that month as zero cost — it renders `Unavailable` (no colour), never a misleading colour. A missing current-month snapshot never triggers this, because the current month is already excluded from the required trend months whenever it is selected.
- **Zero vs. unavailable, now tracked per calendar month:** a cell renders `€ 0,00` only when its month has a valid latest-run snapshot with no matching cost row (a genuine zero); it renders `-` when its month has no valid snapshot at all. A row's `Total` (and the grand `Total` row) renders `-` whenever any of the six displayed months lacks a valid snapshot, rather than silently summing the other five and presenting an incomplete total as complete.
- **Environment grid totals reflect the selected Environment:** the Environment grid's `Total` row is calculated only from the environment(s) currently selected (all of them for `All`, or just the one selected environment otherwise) — it is never an all-environment grand total that happens to get filtered afterwards.

**Validation performed (local/offline only):**

- Bicep build, lint, and `build-params` passed for the module, entrypoint, and LIMS parameter file (standalone `bicep` CLI, since `az` was not available in this session — see the tool note in this milestone's completion report).
- Structural checks against the compiled `serializedData` confirmed **zero** occurrences of `Microsoft.CostManagement`, `queryType: 12`/ARMEndpoint query definitions, or a `CostDataJson` parameter anywhere in the compiled template; `CostManagementSnapshot_CL` is the only table referenced by either grid query; both grid items set an explicit `timeContext.durationMs` of `63072000000`; `serializedData` parses as valid JSON.
- The latest-whole-run selection, six-month windowing, zero-vs-unavailable, Environment filtering, and trend (including fail-closed suppression) logic were ported to a local, offline fixture harness (JavaScript, not committed to the repository) that reimplements the same algorithm the KQL above expresses, run against synthetic `CostManagementSnapshot_CL`-shaped rows. It proved, at minimum: two `CollectionRunId`s for the same `BillingMonth` select only the newest run, with zero leakage from the older run; six displayed months are calendar-correct for both a historical and a current Report Month; a current Report Month excludes the current month from trend while a historical Report Month includes all six; `Environment = All` aggregates every environment while a specific `Environment` filters both grids and changes the Service grid's totals; a valid snapshot with a missing Environment/Service row renders as zero, while a wholly missing monthly snapshot renders as unavailable (and so does its Total); a missing required trend month suppresses the trend to `Unavailable` rather than treating it as zero, while a missing *current*-month snapshot does not suppress the five-completed-month trend; repeated snapshots for the same month do not double-count (only the newest run's rows are summed); and the pre-existing trend threshold classification (stable-by-percentage, stable-by-noise-floor, downward, mild upward, strong upward) is unchanged. **This is fixture-level algorithm validation only — it is not a real Kusto execution, and it does not validate the compiled KQL text runs correctly against the live workspace.**

**Known limitations / outstanding work:**

- **The LAW-backed workbook itself has not been customer-side validated.** No Azure login, deployment, what-if, or RBAC change has been performed from this repository for this workbook. The KQL text has been reviewed and its underlying algorithm fixture-tested (see above), but its actual execution against the live `CostManagementSnapshot_CL` table and the resulting rendered grids have not been observed.
- **Management-group scope caveat (historical, collector-only now):** the Tenant Root Group `managementGroupId` value is no longer used by this workbook to query Cost Management; it remains relevant only to the separate collector's own query scope (see the Snapshot Collector section below), where the same caveat applies — it should not be read as a recommendation to grant tenant-wide Cost Management visibility, and RBAC for the costing security group is reviewed and applied separately by the customer and is intentionally outside this repository's authority — see [`docs/scope.md`](scope.md). This repository does not create, modify, or assign any RBAC.

- This workbook is not customer-approved or presentation-polished; cosmetic aspects (exact trend iconography, explanatory text wording) were intentionally left simple.

### Cost Management LAW Ingestion Foundation — lims

The approved production direction for Cost Management reporting data:

```text
Cost Management API → scheduled collector → normalized monthly cost snapshots →
Logs Ingestion API → existing central Log Analytics workspace →
CostManagementSnapshot_CL → Cost Management workbook
```

This milestone implemented the destination: a custom Log Analytics table plus its Direct-ingestion Data Collection Rule (DCR), against the existing central LIMS reporting Log Analytics workspace (`law-reports-mgmt-westeu`, in `rg-lims-reports-mgmt-westeu`) also used by the Cost Management Dashboard workbook. It has since been deployed and proven live — see below. A collector now writes to it (Snapshot Collector section below) and the workbook now reads from it exclusively (Cost Management Dashboard section above), though the workbook itself remains customer-side unvalidated — see that section's Outstanding work.

- **Reusable module:** [`modules/observability/cost-management-data-foundation/main.bicep`](../modules/observability/cost-management-data-foundation/main.bicep) — creates only `Microsoft.OperationalInsights/workspaces/tables` and `Microsoft.Insights/dataCollectionRules` against an existing, externally-supplied workspace. No workspace, resource group, DCE, identity, or role assignment is created. `tableName` and `dataCollectionRuleName` are parameters, not hard-coded, so the same module is reusable for another project's table/DCR pair.
- **Reusable entrypoint:** [`src/observability/cost-management-data-foundation/main.bicep`](../src/observability/cost-management-data-foundation/main.bicep) — subscription-scoped orchestrator. Both the target subscription and the target resource group are derived from `workspaceResourceId` (its `subscriptions/{id}` and `resourceGroups/{name}` segments) rather than accepted as separate, duplicate parameters; the module is explicitly scoped to `resourceGroup(workspaceSubscriptionId, workspaceResourceGroupName)`, so deployment always targets the workspace's actual subscription regardless of the ambient `az deployment sub create` context.
- **LIMS configuration:** [`config/nfi/lims/observability/cost-management-data-foundation.bicepparam`](../config/nfi/lims/observability/cost-management-data-foundation.bicepparam) — points at the same central workspace already used by the Cost Management Dashboard workbook; `tableName = CostManagementSnapshot_CL`, `dataCollectionRuleName = dcr-cost-snapshot-westeu`, `retentionInDays = totalRetentionInDays = 730`, `dataCollectionEndpointResourceId = ''` (no DCE — see below).
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-cost-management-data-foundation.yml`](../.azuredevops/pipelines/deploy-cost-management-data-foundation.yml) — same commissioning posture as the other two capability pipelines (`trigger: none`, `pr: none`, default `what-if`, explicit `deploy`). Its `what-if` action reuses the existing shared `templates/deploy-observability-workbook-steps.yml`; its `deploy` action does not, because that template's post-deploy step reads workbook-specific output names this composition does not produce — see the pipeline's own header comment for the reuse-decision rationale. **This pipeline has been run successfully and deployed the table/DCR** — see "Current state" below.

**Table schema (append-only, 9 columns):** `TimeGenerated` (datetime, snapshot/collection timestamp — set explicitly by the collector), `Project` (string — this foundation only defines the column; it is not a parameter anywhere in this foundation itself, including `cost-management-data-foundation.bicepparam`; the collector populates it at write time from its own `-Project` pipeline parameter, `lims` for LIMS), `SubscriptionId` (string), `Environment` (string, derived from repository configuration, never from Azure tags), `BillingMonth` (datetime, the authoritative Cost Management billing month), `ServiceName` (string, native Cost Management dimension), `ActualCost` (real), `Currency` (string, currently `EUR` for LIMS but not hard-coded), `CollectionRunId` (string, correlates all rows written by one collector run). The model is append-only by design: repeated collection runs write newer snapshots for the same `Project`/`BillingMonth` logical window; the Cost Management Dashboard workbook (see above) selects the latest complete run per `Project`/`BillingMonth` via `arg_max` over `CollectionRunId`, not per-row. No stored function for this exists; the selection logic lives in the workbook's own KQL. Real data has been ingested — see the Snapshot Collector section below for the historical backfill proof.

**Single-sourced schema, no drift possible by construction:** both the table's `schema.columns` and the DCR stream declaration's columns are generated from one canonical `columnDefinitions` list in the module, via a small per-API type-token map (the table API expects `dateTime`, the DCR stream-declaration API expects `datetime`, for the same logical concept — a documented Azure API inconsistency, not schema drift). Column names and count cannot differ between the two because they are never declared twice.

**Data Collection Rule:** `kind: Direct` (API version `2024-03-11`), one stream (`Custom-CostManagementSnapshot_CL`, derived from the table name rather than duplicated), one Log Analytics destination (the existing workspace only), one data flow with an explicit, schema-preserving `transformKql: 'source'` passthrough (same stream in and out; no mapping/enrichment logic — normalization belongs in the future collector, not here). The Azure Monitor custom-table/DCR workflow requires the table to exist before the DCR targets it; because the data flow references the table only by stream-name string (Bicep cannot infer this ordering on its own), the module adds exactly one explicit `dependsOn` from the DCR to the table — no other `dependsOn` exists in the module.

**DCE deferred, forward-compatible:** LIMS does not have a Data Collection Endpoint yet (insufficient private-networking IP address space for the future design). The DCR works through its own Direct logs-ingestion endpoint today, exposed as this module's `directLogsIngestionEndpoint` output. `dataCollectionEndpointResourceId` is an optional module/entrypoint/config parameter (empty for LIMS today); supplying a DCE resource ID in a future configuration change lets the same module set `properties.dataCollectionEndpointId` on the DCR without any change to the table schema, stream declaration, destination, or data flow. Associating a DCE this way does **not**, by itself, switch where the collector sends data: a Direct DCR may retain its own standalone endpoint even once associated with a DCE, and the caller chooses which endpoint to use. Adopting DCE-routed ingestion therefore needs **two** separate changes, not one: (1) this LIMS configuration file setting `dataCollectionEndpointResourceId`, changing `properties.dataCollectionEndpointId` on the DCR; **and** (2) the future collector's own generic `logsIngestionEndpoint` configuration value being switched, separately, from this module's `directLogsIngestionEndpoint` output to the DCE resource's own `properties.logsIngestion.endpoint`. This module never creates, invents, or resolves a DCE.

**Outputs:** `tableName`, `streamName`, `dataCollectionRuleResourceId`, `dataCollectionRuleImmutableId`, `directLogsIngestionEndpoint`. The last two are read-only, server-populated DCR properties (`properties.immutableId`, `properties.endpoints.logsIngestion`); Bicep resolves them via an implicit `reference()` against the deployed resource symbol — no value is fabricated, and no separate `reference()`/`listKeys()`-style workaround was needed.

**Validation performed (local/offline only):** Bicep build, lint, and `build-params` passed for the module, entrypoint, and LIMS parameter file (also re-run against the pre-existing VM Availability and Cost Management Dashboard files as a regression check — unchanged, zero diagnostics). A structural check against the compiled ARM template confirmed: exactly one custom table and exactly one DCR; table plan `Analytics`; the exact 9-column schema; DCR `kind: Direct`; the DCR's single destination targets the configured workspace resource ID; the data flow is schema-preserving; no DCE, identity, role assignment/definition, or networking resource exists anywhere in the template; the `dataCollectionEndpointResourceId` conditional-property pattern is present; and both immutable-ID and Direct-ingestion-endpoint outputs use `reference()` against the real deployed DCR. A dedicated schema-equivalence test proved the table and stream declarations have identical column names, identical column count, and identical logical column types (after canonicalising the documented `dateTime`/`datetime` casing difference) — and, as a negative control, that the same test correctly detects an intentionally injected one-column drift, proving the test is not vacuous.

**Operational prerequisite — RBAC (external, not performed here):** the identity running the scheduled collector (the Azure DevOps service principal; see below) requires the **Monitoring Metrics Publisher** role at this DCR's scope before it can successfully ingest data through it. That role assignment is outside this repository's authority (see [`docs/scope.md`](scope.md)) and was performed as a separate customer/user action after this DCR was deployed — it was not created, modified, or requested by this repository. **This grant has since been confirmed proven live** (see the Snapshot Collector section below): the real collector has successfully ingested through this DCR.

**Collector host — Azure DevOps now, Logic App later:** the scheduled collector (see the Snapshot Collector section below) runs from Azure DevOps, using the same stable `ClientType: NFI-LIMS-CostCollector` HTTP header proven during customer-side diagnostics. A Logic App is the planned future scheduler/execution host that will eventually replace Azure DevOps for this purpose. This foundation intentionally contains no Azure-DevOps-specific assumptions: the durable ingestion contract is *normalized JSON records + `logsIngestionEndpoint` + DCR immutable ID + stream name*, not a YAML-specific implementation, so the collector host can change later without redesigning the table, DCR, or workbook.

### Cost Management Snapshot Collector — lims (manual commissioning)

The real collector implementing the approved production data path:

```text
Azure DevOps service connection
-> ONE management-group Cost Management query for ONE month
-> normalize the Cost Management response
-> map SubscriptionId to Environment from existing repo config
-> ONE Logs Ingestion API POST
-> CostManagementSnapshot_CL
```

This milestone implements the collector itself and a **manual-only** commissioning pipeline. It does not enable a schedule, and it does not refactor the Cost Management Dashboard workbook — see the two "not yet" points below.

- **Collector script:** [`scripts/observability/Invoke-CostManagementSnapshotCollector.ps1`](../scripts/observability/Invoke-CostManagementSnapshotCollector.ps1) — a straightforward, single-file PowerShell (Core) script. It reads its two authoritative configuration sources at run time via `az bicep build-params --stdout` rather than duplicating any value into a new config file: `managementGroupId` and `subscriptionEnvironmentMappings` remain authoritative in [`cost-management-workbook.bicepparam`](../config/nfi/lims/observability/cost-management-workbook.bicepparam); `workspaceResourceId`, `tableName`, and `dataCollectionRuleName` remain authoritative in [`cost-management-data-foundation.bicepparam`](../config/nfi/lims/observability/cost-management-data-foundation.bicepparam).
- **Commissioning pipeline:** [`.azuredevops/pipelines/collect-cost-management-snapshot.yml`](../.azuredevops/pipelines/collect-cost-management-snapshot.yml) — `trigger: none`, `pr: none`, and **deliberately no `schedules:` block yet**. It is a thin wrapper: a single `AzureCLI@2` step runs the collector script with pipeline parameters (`billingMonth`, `project`, `costParametersFile`, `foundationParametersFile`); no collector logic is duplicated in YAML. **This pipeline has been run successfully**, proving real end-to-end ingestion and completing the March–August 2026 historical backfill — see "Proven live" below.

**Behavior:**

- **Exactly one Cost Management POST per run**, management-group scope, `ActualCost`/`Monthly`, grouped by `SubscriptionId` + `ServiceName`, explicitly filtered to only the configured subscription IDs (never dynamically enumerated), with the proven `ClientType: NFI-LIMS-CostCollector` header. No retry loop and no automatic fallback to subscription-scope queries exist. A `429` response is diagnosed (known throttle headers, if present) and fails the run without ingesting; any other non-2xx response also fails the run without ingesting.
- **Billing month is calendar-accurate**, never a 30-day approximation: `current` uses the first day of the current UTC month through now (a deliberately partial month); an explicit `YYYY-MM` uses that exact calendar month's first day through its last day, `23:59:59Z`, and must name a **completed** historical month — an explicit `YYYY-MM` equal to the current, still-in-progress calendar month is rejected before any Cost Management call is made, with a message telling the operator to use the literal `current` instead. An invalid format or a future month is also rejected up front. The collector never issues a six-month query.
- **Response columns are resolved by name**, from `properties.columns`, the same mechanism already used by the Cost Management Dashboard workbook — never a fixed array position. Fails closed if `Cost`, `BillingMonth`, `SubscriptionId`, `ServiceName`, or `Currency` is absent, if `properties.nextLink` is present (no pagination is followed), or if zero rows are returned (never treated as valid zero-cost data).
- **Environment is derived only from the configured `subscriptionEnvironmentMappings`**, never from Azure tags. A returned `SubscriptionId` that is not present in that configuration fails the run. Multiple subscriptions may map to the same environment.
- **Normalization produces the exact 9-column `CostManagementSnapshot_CL` shape** (`TimeGenerated`, `Project`, `SubscriptionId`, `Environment`, `BillingMonth`, `ServiceName`, `ActualCost`, `Currency`, `CollectionRunId`) with one shared `TimeGenerated` and one shared `CollectionRunId` (`cost-{project}-{billingMonth}-{guid}`) for every row produced by a single run. Rows are not re-pivoted or re-summarized beyond the Cost API's own `SubscriptionId` + `ServiceName` grouping.
- **The DCR immutable ID and Direct logs-ingestion endpoint are never hard-coded.** The script reads the already-deployed DCR live via a read-only `az rest` GET (the same API version used by the foundation module), deriving the target subscription/resource group from `workspaceResourceId` the same way the foundation's reusable entrypoint does, and deriving the stream name as `Custom-${tableName}` from the foundation's own `tableName` parameter rather than inventing a second source of truth. The run fails if either the immutable ID or the endpoint comes back empty.
- **Exactly one Logs Ingestion POST per run**, all normalized rows in a single request body, using an access token scoped to `https://monitor.azure.com/`. No retry loop exists. Ingestion is never attempted if the Cost Management query, schema validation, pagination check, or Environment mapping failed for any row.
- **Append-only, by design:** repeated runs for the same billing month write new snapshot rows rather than updating or deleting existing ones — the Cost Management Dashboard workbook (see above) selects the newest complete `CollectionRunId` per `Project`/`BillingMonth`. This collector does not implement that workbook-side selection logic itself.
- **Logging is deliberately limited:** project, selected billing month, query window, configured subscription count, configured environment names, Cost API HTTP status, Cost row count, currencies returned, `CollectionRunId`, DCR name, ingestion HTTP status, normalized row count, and a final `RESULT: SUCCESS`/`RESULT: FAILED` line. Access tokens, the full Cost Management response, raw subscription IDs, and customer cost totals are not printed (a mapping failure's offending `SubscriptionId` is printed only because it is required to diagnose that specific failure).

**Validation performed (local/offline only):**

- The script's syntax was validated with the PowerShell language parser (`[System.Management.Automation.Language.Parser]::ParseFile`) — zero parse errors.
- The pipeline YAML was validated with a real YAML parser, confirming `trigger: none`, `pr: none`, no `schedules:` block, the expected parameters, and a single `AzureCLI@2` step referencing the collector script by path (no inline duplication of collector logic).
- A local, offline PowerShell fixture harness (outside the repository, not committed) dot-sourced the real script with its `-ImportOnly` switch (the switch, not dot-sourcing by itself, is what skips Main — `AzureCLI@2` also dot-sources the script to run it in the real pipeline) — exercising its actual functions directly, with no Azure/network call — and proved: live-shaped and reordered Cost Management columns normalize identically (name-based resolution, not position-based); a response missing any one of the five required columns fails closed; a paged response (`nextLink` present) fails closed; a zero-row response fails closed; an unmapped `SubscriptionId` fails closed; multiple subscriptions correctly map to the same environment; one collection run produces exactly one shared `CollectionRunId` and `TimeGenerated`; `BillingMonth` parses calendar-correctly; the current-month window is first-of-month-to-now; a historical month uses the exact complete calendar month (including 30-day, 31-day, and February boundaries); a future month, an invalid month format, and an explicit `YYYY-MM` naming the current (incomplete) month are all rejected; and a normalized record contains exactly the 9 `CostManagementSnapshot_CL` columns, for both single-row and multi-row Cost Management responses. The same fixture harness also caught and proved the fix for a genuine single-row edge case (below).
- Structural checks against the script and pipeline source confirmed: exactly one Cost Management POST call site and exactly one Logs Ingestion POST call site; no retry loop; no subscription-scope fallback; the `ClientType` header is present and set to `NFI-LIMS-CostCollector`; the DCR immutable ID and logs-ingestion endpoint are read at run time via `az rest`, never as literals; `managementGroupId` is read from the parameter file, never hard-coded; `subscriptionEnvironmentMappings` is read once from the parameter file and not duplicated elsewhere; no RBAC/Entra/identity resource or mutation, and no `az deployment`/`az resource create`/`az group create` command, appears anywhere in either file; and neither the Cost Management Dashboard workbook files nor the VM Availability SLA Dashboard files were modified.

**A genuine single-row bug was found and fixed during this milestone's own local testing** (not a live/cloud finding): PowerShell's pipeline unwraps a one-element collection returned from a function, and separately serializes a one-element collection piped into `ConvertTo-Json` as a bare JSON object — both of which would have silently corrupted a Cost Management response containing exactly one row (a real possibility, not a hypothetical edge case). The fix is: the normalization function returns its records with a plain `return`, letting PowerShell stream one record object per Cost row to the pipeline exactly as it would for any other count; every call site then wraps that call in `@(...)`, which guarantees a flat array with exactly one element per row regardless of whether zero, one, or many rows were returned; and the Logs Ingestion request body is built with `ConvertTo-Json -InputObject` (not pipeline input), which always serializes that array as a JSON array of record objects, never a bare object and never a nested array. This is covered by dedicated fixture assertions, for both a single-row and a multi-row response, proving: the normalized count equals the input row count; every record has exactly the 9 approved fields; the serialized JSON root is an array; every root array element is a flat record object (no nested array); and the JSON round-trips back to the same row count.

## Continuous Integration

[`.azuredevops/pipelines/ci.yml`](../.azuredevops/pipelines/ci.yml) is the only *automatically triggered* pipeline in this repository. It runs on every push to every branch, including `main`, and performs static validation only — it does not deploy or otherwise mutate Azure. There is no PR-specific trigger. Capability-specific deployment pipelines (see above) exist alongside it but are commissioning-safe and do not trigger automatically.

1. **Bicep build and lint** — every `*.bicep` file in the repository is compiled and linted.
2. **Bicep parameter file validation** — every `*.bicepparam` file is built to confirm it resolves against its composition.
3. **Prohibited resource type guard** — a static search blocks any checked-in Bicep or parameter file that references Microsoft Graph, management-group creation, subscription creation, or role assignment/definition resource types, enforcing the boundaries in [`docs/scope.md`](scope.md).

There is currently no automatic *deployment* pipeline. The three capability deployment pipelines described above (VM Availability SLA Dashboard v2, Cost Management Dashboard, Cost Management LAW Ingestion Foundation) exist alongside `ci.yml`; none triggers automatically (`trigger: none`, `pr: none` on all three) — each must be run manually. The first two share their full validate/what-if/deploy steps via [`.azuredevops/pipelines/templates/deploy-observability-workbook-steps.yml`](../.azuredevops/pipelines/templates/deploy-observability-workbook-steps.yml); the third reuses that same template only for its `what-if` action (its `deploy` action does not fit the template's workbook-specific output handling — see that pipeline's own header comment).

Two further manual, non-deployment pipelines exist for the Cost Management Snapshot Collector milestone, also `trigger: none`/`pr: none` and not triggered by `ci.yml`: [`collect-cost-management-snapshot.yml`](../.azuredevops/pipelines/collect-cost-management-snapshot.yml) (the real collector, no `schedules:` block yet — see above) and the temporary [`test-cost-management-ingestion.yml`](../.azuredevops/pipelines/test-cost-management-ingestion.yml) synthetic-ingestion probe. Neither performs a Bicep deployment; both are kept out of `ci.yml`'s automatic trigger for the same reason as the deployment pipelines — they must never run unattended before their outputs are reviewed.
