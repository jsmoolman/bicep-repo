# Operations

This document describes only the operational behavior that actually exists in this repository today.

## Current state

### VM Availability SLA Dashboard v2 — lims

The first migrated observability capability. This is a lossless migration of a pre-existing, customer-approved LIMS Azure Monitor Workbook from a legacy repository — the workbook's KQL, layout, parameters, and behavior were preserved as-is; only file location and the module reference path changed.

- **Reusable entrypoint:** [`src/observability/vm-availability-sla-dashboard-v2/main.bicep`](../src/observability/vm-availability-sla-dashboard-v2/main.bicep) — subscription-scoped orchestrator, no LIMS-specific values, suitable for reuse by another project with a different parameter file.
- **Reusable module:** [`modules/observability/vm-availability-sla-dashboard-v2/main.bicep`](../modules/observability/vm-availability-sla-dashboard-v2/main.bicep) — the workbook resource definition, migrated unchanged from the legacy implementation.
- **LIMS configuration:** [`config/nfi/lims/observability/vm-availability-sla-dashboard-v2.bicepparam`](../config/nfi/lims/observability/vm-availability-sla-dashboard-v2.bicepparam) — one central workbook covering the `dev`/`tst`/`acc`/`preprd`/`prd` LIMS environments via `subscriptionEnvironmentMappings`, converted from the legacy ARM parameter JSON with all effective values unchanged.
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-vm-availability-sla-dashboard-v2.yml`](../.azuredevops/pipelines/deploy-vm-availability-sla-dashboard-v2.yml) exists but is **temporarily non-triggering** (`trigger: none`, `pr: none`) during commissioning. It supports an explicit `what-if` (default) or `deploy` action and must be run manually. It has not been run from this repository.
- **Live validation status:** No Azure what-if or deployment has been performed from this repository for this capability yet. This migration is a static, local-build-only change. Operational proof (a successful what-if against the live environment, followed by a reviewed deployment) is a separate future step.

**Known legacy naming detail:** the repository/capability name `VM Availability SLA Dashboard v2 - lims` refers to this capability in documentation and file paths only. It is not the literal customer-visible name produced by the deployed workbook. The existing (unchanged) legacy implementation actually produces:

- an in-workbook title of `VM Availability SLA Dashboard v2 — lims` (note: em dash, not a hyphen), and
- an Azure Portal workbook gallery `displayName` of `workbook-vm-availability-v2-lims-westeu`, which does not resemble the descriptive name at all.

This migration intentionally preserved both values unchanged, since the deployed workbook, its resource GUID/name logic, and its customer-visible display name/title must not change as part of relocating the implementation into this repository.

### Cost Management — lims

**Purpose.** Reports LIMS Azure costs by Environment and Service, six calendar months at a time, with a month-over-month Trend on the Service grid.

**Components:**

- **Snapshot Collector:** [`scripts/observability/Invoke-CostManagementSnapshotCollector.ps1`](../scripts/observability/Invoke-CostManagementSnapshotCollector.ps1), run via [`.azuredevops/pipelines/collect-cost-management-snapshot.yml`](../.azuredevops/pipelines/collect-cost-management-snapshot.yml).
- **LAW Ingestion Foundation:** [`modules/observability/cost-management-data-foundation/main.bicep`](../modules/observability/cost-management-data-foundation/main.bicep) / [`src/observability/cost-management-data-foundation/main.bicep`](../src/observability/cost-management-data-foundation/main.bicep) / [`cost-management-data-foundation.bicepparam`](../config/nfi/lims/observability/cost-management-data-foundation.bicepparam), deployed via [`deploy-cost-management-data-foundation.yml`](../.azuredevops/pipelines/deploy-cost-management-data-foundation.yml). Creates the `CostManagementSnapshot_CL` custom table (Analytics plan, 730/730-day retention) and a `kind: Direct` Data Collection Rule (`dcr-cost-snapshot-westeu`) against the existing central workspace `law-reports-mgmt-westeu`. No workspace, DCE, identity, or role assignment is created.
- **Dashboard workbook:** [`modules/observability/cost-management-workbook/main.bicep`](../modules/observability/cost-management-workbook/main.bicep) / [`src/observability/cost-management-workbook/main.bicep`](../src/observability/cost-management-workbook/main.bicep) / [`cost-management-workbook.bicepparam`](../config/nfi/lims/observability/cost-management-workbook.bicepparam), deployed via [`deploy-cost-management-workbook.yml`](../.azuredevops/pipelines/deploy-cost-management-workbook.yml).

**Data flow:**

```text
Azure Cost Management API
  -> Snapshot Collector (one management-group query per month)
  -> Logs Ingestion API / Data Collection Rule
  -> CostManagementSnapshot_CL (Log Analytics, law-reports-mgmt-westeu)
  -> Cost Management Dashboard workbook
```

**How to collect a monthly snapshot.** Run `collect-cost-management-snapshot.yml` manually with `billingMonth` = `current` or a completed `YYYY-MM`. It issues exactly one management-group Cost Management query, resolves response columns by name, maps `SubscriptionId` to `Environment` via `subscriptionEnvironmentMappings`, and performs exactly one Logs Ingestion POST of the normalized 9-column rows. Any validation failure (missing column, `nextLink` pagination, zero rows, unmapped subscription) or non-2xx response from either API aborts the run before ingesting — a failed run never writes partial data. No schedule is configured; this is a manual operation today.

**How to deploy/update the workbook or foundation.** `deploy-cost-management-data-foundation.yml` and `deploy-cost-management-workbook.yml` are both manual (`trigger: none`, `pr: none`), default to `what-if`, and accept an explicit `deploy` action.

**Required permissions/prerequisites:**

- The collector's identity (the Azure DevOps service connection) requires the **Monitoring Metrics Publisher** role at the DCR's scope to ingest data. This role assignment is managed outside this repository — see [`docs/scope.md`](scope.md).
- Read/query access to `law-reports-mgmt-westeu` is required to view the workbook; granted separately.
- Read access to Cost Management at the configured management-group scope is required for the collector to query costs.

**Workbook behavior that matters operationally:**

- The workbook reads only `CostManagementSnapshot_CL`; it never calls the Cost Management API directly.
- The collector's writes are append-only. For each `Project` + `BillingMonth`, the workbook selects only the rows belonging to the newest complete `CollectionRunId` (identified by the `cost-{workloadName}-` prefix, excluding synthetic/diagnostic probes) — never a per-row `arg_max()`, which could mix rows from different runs.
- A cell/Total renders `€ 0,00` only when a valid snapshot exists with genuinely zero matching cost; it renders `-` when no valid snapshot exists for that month.
- The Environment grid's row order follows `subscriptionEnvironmentMappings`' configured order; `Total` is always last.
- The Service grid's `Trend` compares only the selected Report Month against the immediately preceding calendar month (not the six-month window), using cent-rounded aggregates so it matches the displayed money values; it is `-` for the current month or when either month's snapshot is unavailable.
- `managementGroupId` and `subscriptionEnvironmentMappings` in `cost-management-workbook.bicepparam` remain the collector script's own configuration source (read via `az bicep build-params`) — do not remove or restructure them for the workbook alone.

**Known final limitations:**

- The collector is manual-only; no `schedules:` block is configured.
- No Data Collection Endpoint (DCE) is configured; the DCR uses its own Direct ingestion endpoint. Adopting a DCE later requires updating both the foundation's parameter file (`dataCollectionEndpointResourceId`) and the collector's ingestion-endpoint configuration.
- A temporary synthetic Logs Ingestion probe pipeline ([`test-cost-management-ingestion.yml`](../.azuredevops/pipelines/test-cost-management-ingestion.yml)) remains available for diagnostics.

### Backup & Restore Dashboard — lims

Built to the same repository pattern as the Cost Management Dashboard and VM Availability SLA Dashboard v2. This workbook reads **exclusively** from three existing Azure Backup Log Analytics resource-specific tables — `AddonAzureBackupJobs`, `CoreAzureBackup`, `AddonAzureBackupPolicy` — already populated by existing Recovery Services Vault diagnostic settings in the same central Log Analytics workspace the other two workbooks already use. This capability creates or modifies no Recovery Services Vault, backup policy, protected item, diagnostic setting, or RBAC/identity resource, and makes no ARM, Azure Resource Graph, Cost Management, or Recovery Services API call — it only reads already-flowing diagnostic telemetry as KQL.

- **Reusable module:** [`modules/observability/backup-restore-workbook/main.bicep`](../modules/observability/backup-restore-workbook/main.bicep) — no LIMS-specific subscription IDs or workspace ID; all are parameters.
- **Reusable entrypoint:** [`src/observability/backup-restore-workbook/main.bicep`](../src/observability/backup-restore-workbook/main.bicep) — subscription-scoped orchestrator; workbook hosting (subscription/resource group/location) is configured independently from the Log Analytics workspace queried, and is scoped explicitly to `resourceGroup(workbookSubscriptionId, workbookResourceGroupName)` rather than any ambient/service-connection subscription context.
- **LIMS configuration:** [`config/nfi/lims/observability/backup-restore-workbook.bicepparam`](../config/nfi/lims/observability/backup-restore-workbook.bicepparam) — reuses the same LIMS reporting resource group/location, central Log Analytics workspace, and `subscriptionEnvironmentMappings` shape/values already used by the Cost Management Dashboard's parameter file.
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-backup-restore-workbook.yml`](../.azuredevops/pipelines/deploy-backup-restore-workbook.yml) — same commissioning posture as the other two workbook pipelines (`trigger: none`, `pr: none`, default `what-if`, explicit `deploy`), reusing the same shared `templates/deploy-observability-workbook-steps.yml`. **It has not been run from this repository.**

**Design:**

This workbook is a concise, business-facing MVP intended primarily for the monthly customer report (screenshot-driven), with the same LAW-only data model and validity rules proven in the earlier technical revision — only the presentation layer changed.

- **Data source: three existing LAW tables only.** No table, Data Collection Rule, diagnostic setting, or ingestion pipeline is created by this capability — the diagnostic settings that populate `AddonAzureBackupJobs`/`CoreAzureBackup`/`AddonAzureBackupPolicy` already exist and are entirely outside this repository's authority. All backup/restore execution results shown in this workbook come from this LAW telemetry, never from a live Recovery Services/ARM call.
- **Explicit, broad LAW query time context:** every query item sets `timeContext.durationMs` to exactly 730 days (63,072,000,000 ms), identical to the Cost Management workbook, so the Azure portal time picker cannot silently truncate history.
- **Environment is derived only from `subscriptionEnvironmentMappings`, never from a resource/VM/vault name**, via the same standardized `tolower(coalesce(_SubscriptionId, SubscriptionId, extract(...ResourceId...), extract(..._ResourceId...)))` expression across all three tables. A subscription not present in that configuration is excluded from Protected Estate and Backup Policy Evidence, never guessed; for job/restore telemetry it is instead retained and labelled `"Unmapped"`, selectable in the Environment parameter only once such telemetry actually exists.
- **Agreed Backup Strategy is intentionally hard-coded.** The top-of-workbook strategy table (schedule/retention per backup workload) represents the customer-agreed configuration, not a live LAW query — this is an explicit, accepted MVP decision. It is presented next to, and does not itself substitute for, the Backup Policy Evidence grid below it.
- **Backup Policy Evidence comes from `AddonAzureBackupPolicy`** (latest configuration per policy, using the exact discovered schema spelling `DiffBackupDaysofTheWeek`), filtered to an explicit allowlist of the eleven agreed LIMS policy names (configurable via the new `agreedPolicyNames` parameter, populated in the LIMS `.bicepparam` file — including the corrected `backuppolicy-sql-lims-preprd-westeu`) so unrelated built-in/unused policies (`DefaultPolicy`, `EnhancedPolicy`, `HourlyLogBackup`, etc.) never clutter the grid. The grid shows only Environment / Backup Type / Schedule / Retention / State — the long Azure `PolicyName` is never displayed (it remains available internally for allowlist filtering/sort order only), and the raw Schedule/Retention fields are normalized into business-readable text (e.g. `Weekly Friday 22:00 UTC`, `Daily 30 days; Weekly 8 weeks; Monthly 6 months; Yearly 3 years`, `Full: Friday 22:00 UTC; Differential: Mon-Thu 22:00 UTC; Log: every 15 minutes`) — proven live raw-data quirks (brace-wrapped array text such as `{Friday}`, the literal four-character text `"null"` on an unpopulated field, and 12-hour `"10:00:00 PM"` clock text) are corrected rather than passed through. **This workbook does not prove or assert per-item/database policy assignment** — live evidence previously established that `AddonAzureBackupPolicy`'s `PolicyAssociation` rows carry no usable item/database identity field, so no such correlation is attempted anywhere in this module (this is why the earlier SQL Log Continuity gap-analysis grid, which depended on no such correlation for its per-database frequency column, has been removed for this MVP — the SQL Log backup class's activity remains fully visible in the Backup Activity and Six-Month grids and, on failure, in Backup Failures).
- **Backup Activity — {ReportMonth} (Hero grid)** is selected-month-only (never a six-month cumulative total), oriented with backup classes as columns — in the fixed visible order `VM Backup` / `SQL Full` / `SQL Differential` / `SQL Log`, matching the Agreed Backup Strategy table, enforced by an explicit final `project` rather than left to `evaluate pivot()`'s own (alphabetical) ordering — and Executed/Succeeded/Failed/Success % as rows. There is no Trend row in this business-presentation revision (the previously computed OLS-regression trend, and all of its now-dead supporting KQL, has been removed); the Six-Month Backup Performance grid immediately below provides historical context instead. A month with no telemetry renders `-` throughout; a month with telemetry but zero executions of a class renders a real `0` for Executed/Succeeded/Failed and `-` (never a fabricated `100%`) for Success %. The current month always shows real month-to-date counts (never suppressed).
- **Backup Failures — {ReportMonth}** (immediately after Backup Activity) is a concise exception report — Time / Environment / Backup Class / Failure Reason only (`Backup Item / Datasource` has been removed from this business presentation) — built from the exact same filtered job base as the Hero grid, so its row count always equals the sum of the Hero grid's own Failed values for the same Report Month/Environment selection. The two `JobFailureCode` values proven live to date are humanized (`UserErrorOpeningSQLConnection` → "Unable to open SQL connection", `UserErrorOperationFailedTargetSQLServerInSingleUserMode` → "SQL Server was in single-user mode"); any other/future code displays its own raw text rather than being hidden.
- **Six-Month Backup Performance** (immediately after Backup Failures) shows Success % per class per calendar month (Report Month + five preceding), oriented with months as rows and the same fixed `VM Backup` / `SQL Full` / `SQL Differential` / `SQL Log` column order as the Hero grid — the historical counterpart to the Hero grid, which never repeats Executed/Succeeded/Failed totals (available by selecting an older Report Month instead).
- **Restore Activity / Restore Details** reuse the existing `JobOperation in~ ("Restore", "Recovery")` detection logic (JobUniqueId-deduplicated, scoped to the selected Report Month), with restore categories derived only from whichever of `Restore`/`Recovery` actually occurred that month — never a fixed or fabricated taxonomy. **Absence of restore/recovery activity for a given month is reported as exactly that (a single concise no-data message on Restore Activity) and is not treated as a compliance failure or a fabricated zero-activity row.** Restore Details is now conditionally hidden — via a documented Azure Workbooks `conditionalVisibility` condition driven by a hidden, query-backed `RestoreDataPresent` parameter (never shown in the visible parameter bar) — whenever there is no restore/recovery evidence for the selected Report Month/Environment, so no second, duplicate no-data message is ever shown; when restore data does exist, Restore Details renders normally and reconciles with Restore Activity's own Executed total.
- **Protected Estate** (moved to immediately before the footer in this revision — its own data/query logic is unchanged) is a compact, live-calculated Environment / Protected VMs / SQL Hosts / Protected SQL Databases grid from `CoreAzureBackup`, filterable by the Environment selector (`All` shows every configured environment; a named Environment shows only that one row).
- **Visible section order** is now: Parameters → Agreed Backup Strategy → Backup Policy Evidence → Backup Activity → Backup Failures → Six-Month Backup Performance → Restore Activity → Restore Details → Protected Estate → footer. Every visible item also sets the same small explicit `styleSettings.margin` (a documented per-item Workbooks JSON property) for consistent, screenshot-friendly compact spacing between sections.
- **Canonical backup classes and success/failure definitions are unchanged:** Succeeded requires `JobStatus =~ "Completed"` **and** `JobFailureCode =~ "Success"`; Failed requires only `JobStatus =~ "Failed"`; any other status counts toward Executed but is neither.

**Validation performed (local/offline only):**

- Bicep build, lint, and `build-params` passed for the module, entrypoint, and LIMS parameter file (standalone `bicep` CLI) — none of which changed in this presentation-cleanup revision except the module itself.
- Structural checks against the compiled ARM template confirmed: exactly one `Microsoft.Insights/workbooks` resource; the same deterministic name (`guid(workloadName, workspaceResourceId, 'backup-restore-workbook')`) and `sourceId`; no `Microsoft.RecoveryServices`, `Microsoft.Authorization`, or diagnostic-settings reference; every query item's `queryType` is `0` (LAW KQL only); only `AddonAzureBackupJobs`/`CoreAzureBackup`/`AddonAzureBackupPolicy` are referenced; the visible item order matches the list above; the Hero grid contains exactly Executed/Succeeded/Failed/Success % (no Trend row) with the fixed `VM Backup`/`SQL Full`/`SQL Differential`/`SQL Log` column order, and the Six-Month grid uses the identical column order; the Backup Failures grid's visible columns are exactly Time/Environment/Backup Class/Failure Reason; the Policy Evidence grid's visible columns are exactly Environment/Backup Type/Schedule/Retention/State with no `PolicyName` in the projection and the `backuppolicy-sql-lims-preprd-westeu` allowlist entry unchanged; Restore Details carries a `conditionalVisibility` condition on the hidden `RestoreDataPresent` parameter and no other item does; and no new resource, table, or query data source was introduced.
- A local, offline JavaScript fixture harness (not committed to the repository) covering: the previously-proven semantic behaviors (zero-vs-Unavailable rendering, `Environment=All`/"Unmapped" handling, six-month window correctness, Hero/Failures reconciliation) plus new coverage added for this revision — `CleanText` stripping brace-wrapped array text and normalizing the literal `"null"` text to empty; `FormatTime24` converting proven 12-hour clock text (e.g. `"10:00:00 PM"`) to `"22:00 UTC"` and falling back to readable raw text plus `" UTC"` for an unrecognized shape; `FormatDays`/`DayAbbrev` rendering a single day by its full name and the proven four-day Monday-Thursday differential list as `"Mon-Thu"`; the full VM/Management VM/SQL Backup Schedule and Retention strings matching the desired business examples exactly; `FormatFailureReason` humanizing both proven live codes and falling back to raw text for an unknown code; and the Restore Details conditional-visibility decision (`RestoreDataPresent` = "No" when zero restore rows, "Yes" and visible otherwise).

**Known limitations / outstanding work:**

- **The rendered output of this specific business-facing layout has not been customer-side validated from this repository.** The KQL text has been reviewed and its underlying algorithm fixture-tested (see above); this repository has performed no Azure login, deployment, what-if, or RBAC change for this revision.
- **Restore-test compliance is not asserted.** Absence of restore/recovery evidence in LAW is reported as exactly that — not as a pass or fail against any business continuity requirement.
- **Policy compliance is not asserted.** Backup Policy Evidence reports the actual current `AddonAzureBackupPolicy` configuration only (filtered to the agreed LIMS policy names); strict compliance logic is deliberately deferred pending an authoritative policy strategy document (e.g. Confluence).
- **No backup resource is managed by this workbook.** It creates/modifies no Recovery Services Vault, backup policy, protected item, diagnostic setting, or RBAC/identity — those all remain entirely outside this repository's authority.
- Viewing this workbook requires read/query access to the configured Log Analytics workspace; that access is reviewed and granted separately and is not part of this deployment.

No other operational capability (alerts, Logic Apps, VM maintenance, or other scripts under `operations/`) has been implemented yet.

## Continuous Integration

[`.azuredevops/pipelines/ci.yml`](../.azuredevops/pipelines/ci.yml) is the only *automatically triggered* pipeline in this repository. It runs on every push to every branch, including `main`, and performs static validation only — it does not deploy or otherwise mutate Azure. There is no PR-specific trigger. Capability-specific deployment pipelines (see above) exist alongside it but are commissioning-safe and do not trigger automatically.

1. **Bicep build and lint** — every `*.bicep` file in the repository is compiled and linted.
2. **Bicep parameter file validation** — every `*.bicepparam` file is built to confirm it resolves against its composition.
3. **Prohibited resource type guard** — a static search blocks any checked-in Bicep or parameter file that references Microsoft Graph, management-group creation, subscription creation, or role assignment/definition resource types, enforcing the boundaries in [`docs/scope.md`](scope.md).

There is currently no automatic *deployment* pipeline. The four capability deployment pipelines described above (VM Availability SLA Dashboard v2, Cost Management Dashboard, Cost Management LAW Ingestion Foundation, Backup & Restore Dashboard) exist alongside `ci.yml`; none triggers automatically (`trigger: none`, `pr: none` on all four) — each must be run manually. The VM Availability, Cost Management, and Backup & Restore workbook pipelines share their full validate/what-if/deploy steps via [`.azuredevops/pipelines/templates/deploy-observability-workbook-steps.yml`](../.azuredevops/pipelines/templates/deploy-observability-workbook-steps.yml); the LAW Ingestion Foundation pipeline reuses that same template only for its `what-if` action (its `deploy` action does not fit the template's workbook-specific output handling — see that pipeline's own header comment).

Two further manual, non-deployment pipelines exist for Cost Management, also `trigger: none`/`pr: none` and not triggered by `ci.yml`: [`collect-cost-management-snapshot.yml`](../.azuredevops/pipelines/collect-cost-management-snapshot.yml) (the collector, no `schedules:` block — see above) and the temporary [`test-cost-management-ingestion.yml`](../.azuredevops/pipelines/test-cost-management-ingestion.yml) synthetic-ingestion probe. Neither performs a Bicep deployment; both are kept out of `ci.yml`'s automatic trigger for the same reason as the deployment pipelines — they must never run unattended before their outputs are reviewed.
