### VM Availability SLA Dashboard v2 — lims

The first migrated observability capability. This is a lossless migration of a pre-existing, customer-approved LIMS Azure Monitor Workbook from a legacy repository — the workbook's KQL, layout, parameters, and behavior were preserved as-is; only file location and the module reference path changed.

- **Reusable entrypoint:** [`src/observability/vm-availability-sla-dashboard-v2/main.bicep`](../src/observability/vm-availability-sla-dashboard-v2/main.bicep) — subscription-scoped orchestrator, no LIMS-specific values, suitable for reuse by another project with a different parameter file.
- **Reusable module:** [`modules/observability/vm-availability-sla-dashboard-v2/main.bicep`](../modules/observability/vm-availability-sla-dashboard-v2/main.bicep) — the workbook resource definition, migrated unchanged from the legacy implementation.
- **LIMS configuration:** [`config/nfi/lims/observability/vm-availability-sla-dashboard-v2.bicepparam`](../config/nfi/lims/observability/vm-availability-sla-dashboard-v2.bicepparam) — one central workbook covering the `dev`/`tst`/`acc`/`preprd`/`prd` LIMS environments via `subscriptionEnvironmentMappings`, converted from the legacy ARM parameter JSON with all effective values unchanged.
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-vm-availability-sla-dashboard-v2.yml`](../.azuredevops/pipelines/deploy-vm-availability-sla-dashboard-v2.yml) exists but is **temporarily non-triggering** (`trigger: none`, `pr: none`) during commissioning. It supports an explicit `what-if` (default) or `deploy` action and must be run manually. It has not been run from this repository.
- **Live validation status:** No Azure what-if or deployment has been performed from this repository for this capability yet. This migration is a static, local-build-only change. Operational proof (a successful what-if against the live environment, followed by a reviewed deployment) is a separate future step.

**Known legacy naming detail:** the repository/capability name `VM Availability SLA Dashboard v2 - lims` refers to this capability in documentation and file paths only. It is not the literal customer-visible name produced by the deployed workbook. The existing (unchanged) legacy implementation actually produces:

- an in-workbook title of `VM Availability SLA Dashboard v2 — lims` (note: em dash, not a hyphen), and
- an Azure Portal workbook gallery `displayName` of `workbook-vm-availability-v2-lims-westeu`, which does not resemble the descriptive name at all.

This migration intentionally preserved both values unchanged, since the deployed workbook, its resource GUID/name logic, and its customer-visible display name/title must not change as part of relocating the implementation into this repository.

### Cost Management Dashboard — lims (single-query pivot POC)

A from-scratch proof of concept, built to the same repository pattern as the VM Availability SLA Dashboard v2. Its core objective is architectural: prove that **one** management-group-scoped Azure Cost Management query per selected Report Month can drive both an Environment cost pivot and a Service cost pivot, without querying subscriptions individually and without Environment selection ever triggering a second Cost Management API call.

> **Superseded production data path.** This workbook's direct, interactive Cost Management API query (described in full below) proved the query shape and is still the current implementation, but it is **no longer the intended production data path**. A customer-side live test (management group, one calendar month, all six configured LIMS subscriptions, `ClientType: NFI-LIMS-CostCollector`) succeeded — `HTTP 200`, ~4.3s, 54 rows, `nextLink` empty, currency `EUR`, all six subscriptions/environments represented — but repeated ad-hoc interactive querying at this scope is not the approved long-term design. The approved direction is a scheduled collector writing normalized snapshots into a persisted Log Analytics table (`CostManagementSnapshot_CL`), described in the next section; the workbook itself has **not yet** been refactored to read from that table. Until that refactor happens, this section continues to describe the workbook's actual current behavior.

- **Reusable module:** [`modules/observability/cost-management-workbook/main.bicep`](../modules/observability/cost-management-workbook/main.bicep) — no LIMS-specific subscription IDs, management-group ID, or workspace ID; all are parameters.
- **Reusable entrypoint:** [`src/observability/cost-management-workbook/main.bicep`](../src/observability/cost-management-workbook/main.bicep) — subscription-scoped orchestrator; workbook hosting (subscription/resource group/location) is configured independently from the Cost Management query scope (management group).
- **LIMS configuration:** [`config/nfi/lims/observability/cost-management-workbook.bicepparam`](../config/nfi/lims/observability/cost-management-workbook.bicepparam) — reuses the existing LIMS reporting resource group/location and the existing central Log Analytics workspace; the management-group ID is the Tenant Root Group (`c7adbc6a-e0b3-4eb7-9403-ed7f7f48ec4b`), a **query-scope decision only**, per explicit customer confirmation — see the caveat below.
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-cost-management-workbook.yml`](../.azuredevops/pipelines/deploy-cost-management-workbook.yml) — same commissioning posture as the VM Availability pipeline (`trigger: none`, `pr: none`, default `what-if`, explicit `deploy`). It has not been run from this repository.

**Design:**

- **One Cost Management query, management-group scope:** a single hidden workbook parameter issues one `Microsoft.CostManagement/query` POST at the configured management group, `type: ActualCost`, `granularity: Monthly`, grouped by `SubscriptionId` and the native Cost Management `ServiceName` dimension, **explicitly filtered** (`In` operator) to only the subscription IDs listed in `subscriptionEnvironmentMappings` — subscriptions are never dynamically enumerated from the management group. The Cost Management API version is pinned in the module (`2026-06-01`), not exposed as a parameter.
- **Static subscription/environment mapping:** identical mechanism to the VM Availability workbook's `subscriptionEnvironmentMappings` — repository configuration is authoritative for which subscriptions are included and how they map to `mgt`/`dev`/`tst`/`acc`/`preprd`/`prd`.
- **Report Month drives the query window; Environment does not:** two further hidden parameters compute the Cost Management request's `from`/`to` date range from the selected Report Month using calendar-month arithmetic (never a 30-day approximation). The `Environment` selector is never referenced anywhere in the query construction — changing it can only re-filter the already-retrieved result.
- **Six-month window, calendar-accurate:** every grid shows the selected Report Month plus the five preceding calendar months, labelled with real `YYYY-MM` values.
- **Pivot and trend run as Log Analytics KQL against the existing central LAW, used purely as a stateless compute engine:** because pure Workbook JSON cannot pivot by calendar month or perform linear regression, the single Cost Management JSON result is passed into ordinary KQL (`mv-expand`, `evaluate pivot()`, manual ordinary-least-squares regression) executed against the same central Log Analytics workspace already used by the VM Availability workbook. **No Cost Management data is ingested into, stored in, or queried from that workspace** — no tables, DCRs, saved searches, or functions are created; the workspace is reused exclusively as a query-execution engine for data that is already in memory as a workbook parameter.
- **Trend:** ordinary least-squares linear regression over completed months only (the current month-to-date is always excluded). Classification applies a €10/month absolute noise floor first (below it, always `Stable`), then `Downward` (≤ -3%), `Stable` (-3%..+3%), `Mild Upward` (+3%..+10%), `Strong Upward` (≥ +10%).
- **Zero vs. unavailable:** a valid query response with no cost for a given month/environment/service renders as `€ 0,00`; a genuinely unusable Cost Management response renders as `-`.
- **Environment grid totals reflect the selected Environment:** the Environment grid's `Total` row is calculated only from the environment(s) currently selected (all of them for `All`, or just the one selected environment otherwise) — it is never an all-environment grand total that happens to get filtered afterwards.
- **Pagination fails closed:** the Cost Management response's `properties.nextLink` is inspected. This workbook intentionally issues only one Cost Management request per Report Month and never follows `nextLink` (no pagination loop, no second query). If a response comes back paged (`nextLink` present), the dataset is treated as unusable for that Report Month and both grids show `-` with a visible warning banner in the title text, rather than presenting first-page figures as complete totals.
- **Response columns are resolved by name, not fixed position.** A customer-side read-only commissioning probe proved the live Cost Management response schema — `Cost` (Number), `BillingMonth` (Datetime, e.g. `2026-07-01T00:00:00`), `SubscriptionId` (String), `ServiceName` (String), `Currency` (String) — with `BillingMonth` at index 1, not the position originally assumed. The parser now reads `properties.columns[].name` to resolve each required column's index at query time, so it stays correct even if Azure returns the same named columns in a different order. `BillingMonth` is the authoritative source for each row's calendar month (parsed as a real datetime, never inferred from array position). If any of the five required columns is absent, the dataset is treated as unusable (same fail-closed `-` behavior as pagination) and the visible warning names the missing column(s).

**Validation performed (local/offline only):**

- Bicep build, lint, and `build-params` passed for the module, entrypoint, and LIMS parameter file.
- Structural checks against the compiled `serializedData` confirmed: exactly one ARMEndpoint (`queryType: 12`) query in the whole template; exactly one `Microsoft.CostManagement/query` path reference; management-group-scoped path; explicit config-driven subscription filter; `Environment` absent from the upstream query construction; `ReportMonth` present in the date-window parameters; both grids reference the shared Cost Management result parameter; `CostDataJson` is injected via the documented `{CostDataJson:escapejson}` formatter (not raw substitution); `properties.nextLink` is explicitly inspected and gates data availability; the Environment grid's Total row is computed from the already environment-filtered subset; column indexes are resolved from `properties.columns` by name (not fixed `Row[0..3]` positions); `BillingMonth` drives month parsing via a parsed datetime, not substring/positional logic.
- The pivot, zero/no-data, and trend classification algorithms (including the six required synthetic scenarios: stable-by-percentage, stable-by-noise-floor, downward, mild upward, strong upward, current-month-excludes-partial-month, historical-month-uses-all-six) were ported to a local JS fixture harness and verified to produce the expected classifications and formatted values. The fixture was extended to also prove: Environment-specific Total-row correctness (an `All` grand total and independent per-environment grand totals, including month-column totals); pagination fail-closed behavior (a `nextLink`-bearing response never produces a displayed total); that the `escapejson`-formatted `CostDataJson` substitution round-trips to valid, byte-identical JSON through KQL string-literal unescaping semantics; that the exact proven live-schema response (Cost, BillingMonth, SubscriptionId, ServiceName, Currency) parses correctly; that the same five columns returned in a deliberately different order produce an identical normalized result (proving name-based, not positional, resolution); and that a response missing any one of `BillingMonth`, `ServiceName`, or `Currency` fails closed (no rows parsed, grids show `-`).

**Known limitations / outstanding work:**

- **A customer-side read-only commissioning probe has proven the management-group query and response schema for one Report Month and one subscription.** The probe confirmed: the management-group-scoped `ActualCost`/Monthly query succeeds; the returned columns are `Cost`, `BillingMonth`, `SubscriptionId`, `ServiceName`, `Currency`; currency is `EUR` for LIMS; the response was a single unpaged page (`nextLink` empty) for that probe. **This does not validate** the full six-month, multi-subscription query shape used in production, the workbook UI, or a full deployment — those remain outstanding. No Azure login, deployment, what-if, or RBAC change has been performed from this repository.
- **Management-group scope caveat:** using the Tenant Root Group as the query scope is a query-scope decision only, made because the query already explicitly filters to the configured LIMS subscriptions. It should not be read as a recommendation to grant tenant-wide Cost Management visibility. RBAC for the costing security group (both Cost Management access at the management-group scope and read/query access to the configured Log Analytics workspace) is reviewed and applied separately by the customer and is intentionally outside this repository's authority — see [`docs/scope.md`](scope.md). This repository does not create, modify, or assign any RBAC.
- This POC is not customer-approved or presentation-polished; cosmetic aspects (exact trend iconography, explanatory text wording) were intentionally left simple per the milestone scope.

### Cost Management LAW Ingestion Foundation — lims

The approved production direction for Cost Management reporting data:

```text
Cost Management API → scheduled collector → normalized monthly cost snapshots →
Logs Ingestion API → existing central Log Analytics workspace →
CostManagementSnapshot_CL → Cost Management workbook
```

This milestone implements **only the destination**: a custom Log Analytics table plus its Direct-ingestion Data Collection Rule (DCR), against the existing central LIMS reporting Log Analytics workspace (`law-reports-mgmt-westeu`, in `rg-lims-reports-mgmt-westeu`) already reused by the Cost Management Dashboard workbook. **No scheduled collector and no workbook refactor are implemented yet** — see Outstanding work below.

- **Reusable module:** [`modules/observability/cost-management-data-foundation/main.bicep`](../modules/observability/cost-management-data-foundation/main.bicep) — creates only `Microsoft.OperationalInsights/workspaces/tables` and `Microsoft.Insights/dataCollectionRules` against an existing, externally-supplied workspace. No workspace, resource group, DCE, identity, or role assignment is created. `tableName` and `dataCollectionRuleName` are parameters, not hard-coded, so the same module is reusable for another project's table/DCR pair.
- **Reusable entrypoint:** [`src/observability/cost-management-data-foundation/main.bicep`](../src/observability/cost-management-data-foundation/main.bicep) — subscription-scoped orchestrator. The target resource group is derived from `workspaceResourceId` (its `resourceGroups/{name}` segment) rather than accepted as a second, duplicate parameter.
- **LIMS configuration:** [`config/nfi/lims/observability/cost-management-data-foundation.bicepparam`](../config/nfi/lims/observability/cost-management-data-foundation.bicepparam) — points at the same central workspace already used by the Cost Management Dashboard workbook; `tableName = CostManagementSnapshot_CL`, `dataCollectionRuleName = dcr-cost-management-snapshot-westeu`, `retentionInDays = totalRetentionInDays = 730`, `dataCollectionEndpointResourceId = ''` (no DCE — see below).
- **Deployment pipeline:** [`.azuredevops/pipelines/deploy-cost-management-data-foundation.yml`](../.azuredevops/pipelines/deploy-cost-management-data-foundation.yml) — same commissioning posture as the other two capability pipelines (`trigger: none`, `pr: none`, default `what-if`, explicit `deploy`). Its `what-if` action reuses the existing shared `templates/deploy-observability-workbook-steps.yml`; its `deploy` action does not, because that template's post-deploy step reads workbook-specific output names this composition does not produce — see the pipeline's own header comment for the reuse-decision rationale. **This pipeline has not been run.**

**Table schema (append-only, 9 columns):** `TimeGenerated` (datetime, snapshot/collection timestamp — set explicitly by the future collector), `Project` (string, e.g. `lims` — not hard-coded into the table/DCR, only into the LIMS parameter file), `SubscriptionId` (string), `Environment` (string, derived from repository configuration, never from Azure tags), `BillingMonth` (datetime, the authoritative Cost Management billing month), `ServiceName` (string, native Cost Management dimension), `ActualCost` (real), `Currency` (string, currently `EUR` for LIMS but not hard-coded), `CollectionRunId` (string, correlates all rows written by one future collector run). The model is append-only by design: repeated collection runs write newer snapshots for the same `Project`/`SubscriptionId`/`BillingMonth`/`ServiceName` logical record; a future consumer selects the latest with `summarize arg_max(TimeGenerated, *) by Project, SubscriptionId, BillingMonth, ServiceName`. No stored function for this exists yet, and no data has been ingested.

**Single-sourced schema, no drift possible by construction:** both the table's `schema.columns` and the DCR stream declaration's columns are generated from one canonical `columnDefinitions` list in the module, via a small per-API type-token map (the table API expects `dateTime`, the DCR stream-declaration API expects `datetime`, for the same logical concept — a documented Azure API inconsistency, not schema drift). Column names and count cannot differ between the two because they are never declared twice.

**Data Collection Rule:** `kind: Direct` (API version `2024-03-11`), one stream (`Custom-CostManagementSnapshot_CL`, derived from the table name rather than duplicated), one Log Analytics destination (the existing workspace only), one schema-preserving data flow (same stream in and out, no `transformKql`). The Azure Monitor custom-table/DCR workflow requires the table to exist before the DCR targets it; because the data flow references the table only by stream-name string (Bicep cannot infer this ordering on its own), the module adds exactly one explicit `dependsOn` from the DCR to the table — no other `dependsOn` exists in the module.

**DCE deferred, forward-compatible:** LIMS does not have a Data Collection Endpoint yet (insufficient private-networking IP address space for the future design). The DCR works through its own Direct logs-ingestion endpoint today. `dataCollectionEndpointResourceId` is an optional module/entrypoint/config parameter (empty for LIMS today); supplying a DCE resource ID in a future configuration change lets the same module set `properties.dataCollectionEndpointId` without any change to the table schema, stream declaration, destination, data flow, or the future collector/workbook ingestion contract. This module never creates or invents a DCE.

**Outputs:** `tableName`, `streamName`, `dataCollectionRuleResourceId`, `dataCollectionRuleImmutableId`, `directLogsIngestionEndpoint`. The last two are read-only, server-populated DCR properties (`properties.immutableId`, `properties.endpoints.logsIngestion`); Bicep resolves them via an implicit `reference()` against the deployed resource symbol — no value is fabricated, and no separate `reference()`/`listKeys()`-style workaround was needed.

**Validation performed (local/offline only):** Bicep build, lint, and `build-params` passed for the module, entrypoint, and LIMS parameter file (also re-run against the pre-existing VM Availability and Cost Management Dashboard files as a regression check — unchanged, zero diagnostics). A structural check against the compiled ARM template confirmed: exactly one custom table and exactly one DCR; table plan `Analytics`; the exact 9-column schema; DCR `kind: Direct`; the DCR's single destination targets the configured workspace resource ID; the data flow is schema-preserving; no DCE, identity, role assignment/definition, or networking resource exists anywhere in the template; the `dataCollectionEndpointResourceId` conditional-property pattern is present; and both immutable-ID and Direct-ingestion-endpoint outputs use `reference()` against the real deployed DCR. A dedicated schema-equivalence test proved the table and stream declarations have identical column names, identical column count, and identical logical column types (after canonicalising the documented `dateTime`/`datetime` casing difference) — and, as a negative control, that the same test correctly detects an intentionally injected one-column drift, proving the test is not vacuous.

**Operational prerequisite — RBAC (external, not performed here):** the identity that will eventually run the scheduled collector (currently expected to be the Azure DevOps service principal; see below) requires the **Monitoring Metrics Publisher** role at this DCR's scope before it can successfully ingest data through it. That role assignment is outside this repository's authority (see [`docs/scope.md`](scope.md)) and is a separate customer/user action performed after this DCR exists — it is not created, modified, or requested by this repository.

**Collector host — Azure DevOps now, Logic App later:** the initial scheduled collector (not yet implemented) will run from Azure DevOps, using the same stable `ClientType: NFI-LIMS-CostCollector` HTTP header proven during customer-side diagnostics. A Logic App is the planned future scheduler/execution host that will eventually replace Azure DevOps for this purpose. This foundation intentionally contains no Azure-DevOps-specific assumptions: the durable ingestion contract is *normalized JSON records + `logsIngestionEndpoint` + DCR immutable ID + stream name*, not a YAML-specific implementation, so the collector host can change later without redesigning the table, DCR, or workbook.

**Outstanding work (not implemented in this milestone):**

- The scheduled collector itself (the component that calls the Cost Management API and writes normalized snapshots via the Logs Ingestion API) does not exist yet.
- The Cost Management Dashboard workbook has **not** been refactored to read from `CostManagementSnapshot_CL` — it still queries Cost Management directly and interactively, as described in the previous section.
- No data has ever been written to `CostManagementSnapshot_CL`; no ingestion test has been performed. An ingestion test is only appropriate after this table/DCR is deployed and the RBAC prerequisite above is granted.
- The table and DCR defined here have **not been deployed** — no `what-if` or `az deployment ... create` has been run from this repository for this capability.
- A DCE remains deferred (see above); when the customer's private-networking design provides one, only the LIMS parameter file needs to change.

No other operational capability (alerts, Logic Apps, VM maintenance, backup automation, or scripts under `operations/`) has been implemented yet.

## Continuous Integration

[`.azuredevops/pipelines/ci.yml`](../.azuredevops/pipelines/ci.yml) is the only *automatically triggered* pipeline in this repository. It runs on every push to every branch, including `main`, and performs static validation only — it does not deploy or otherwise mutate Azure. There is no PR-specific trigger. Capability-specific deployment pipelines (see above) exist alongside it but are commissioning-safe and do not trigger automatically.

1. **Bicep build and lint** — every `*.bicep` file in the repository is compiled and linted.
2. **Bicep parameter file validation** — every `*.bicepparam` file is built to confirm it resolves against its composition.
3. **Prohibited resource type guard** — a static search blocks any checked-in Bicep or parameter file that references Microsoft Graph, management-group creation, subscription creation, or role assignment/definition resource types, enforcing the boundaries in [`docs/scope.md`](scope.md).

There is currently no automatic *deployment* pipeline. The three capability deployment pipelines described above (VM Availability SLA Dashboard v2, Cost Management Dashboard, Cost Management LAW Ingestion Foundation) exist alongside `ci.yml`; none triggers automatically (`trigger: none`, `pr: none` on all three) — each must be run manually. The first two share their full validate/what-if/deploy steps via [`.azuredevops/pipelines/templates/deploy-observability-workbook-steps.yml`](../.azuredevops/pipelines/templates/deploy-observability-workbook-steps.yml); the third reuses that same template only for its `what-if` action (its `deploy` action does not fit the template's workbook-specific output handling — see that pipeline's own header comment).
