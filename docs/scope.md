# Repository Scope

This repository is a foundation for **Azure operational automation, observability, reporting, and approved maintenance-as-code**. It is not a general Azure Landing Zone or tenant-provisioning framework.

This document defines the three scope categories that apply to everything deployed from this repository.

## Allowed by default

### Observability

- Azure Monitor workbooks
- Azure dashboards
- Availability reporting
- Cost/costing workbooks
- Metric alerts
- Log/scheduled-query alerts
- Activity/service-health style alerts where appropriate
- Alert processing rules
- Saved operational queries
- Monitoring configuration
- Diagnostic settings where justified
- Data collection configuration where justified

### Security monitoring

Where permissions allow and without any identity change:

- Sentinel workbooks
- Sentinel analytics/detection content
- Sentinel operational configuration
- Defender-related monitoring/alerting configuration where specifically required

Subscription-wide Defender configuration is **not** automatically allowed — it requires an explicit decision (see below).

### Automation and maintenance

- Logic Apps used primarily for maintenance, observability, reporting, backup orchestration, operational notifications, or operational remediation
- VM lifecycle operations (start, stop, deallocate, restart) where explicitly implemented for operational purposes
- Health checks, reporting, and approved maintenance tasks

Logic Apps are an approved resource type in this repository when their purpose aligns with this operational scope, and provided they introduce no prohibited identity changes.

### Cross-project reusable services

Reusable observability/costing capabilities may target another subscription, multiple subscriptions, or a management-group scope, without duplicating implementation per target. Targeting is controlled through configuration, not through duplicated Bicep.

## Explicit architecture decision required

The following are not treated as normal repository authority. Each requires a separate, specific decision before implementation:

- Networking changes (including new IP-range assignment/configuration)
- Policy assignments
- RBAC
- Subscription configuration
- Resource locks
- Infrastructure creation (virtual networks, subnets, firewalls, route tables, private endpoints, virtual machines, VM scale sets, storage infrastructure, SQL/database infrastructure, Key Vault infrastructure, application hosting infrastructure, management groups, subscription vending, resource-group topology, general landing-zone/platform infrastructure)
- Security posture changes outside operational monitoring
- Anything destructive beyond a specifically designed and approved maintenance operation

Once a specific decision of this kind is made, it is recorded as a named, narrowly scoped exception below — it does not become general repository authority, and it does not authorize anything beyond what the exception explicitly states.

### RBAC and Entra ID mutation are distinct

RBAC appears in the list above because any RBAC assignment still requires a separate, specific, approved decision before implementation — it is never default repository authority. However, RBAC assignment of an already-existing Entra principal is **not** itself a form of Entra ID mutation, and must not be documented or guarded as one.

Prohibited as Entra ID mutation (see "Prohibited" below — this is unaffected and unchanged):

- Creating or modifying Entra users
- Creating or modifying Entra groups
- Changing Entra group membership
- Application registrations or enterprise applications
- Service principals
- Directory roles
- Microsoft Graph mutations
- General Entra identity lifecycle management

Not prohibited as Entra ID mutation:

- Assigning an already-existing Entra object/principal to an Azure RBAC role.

This is still subject to the "Explicit architecture decision required" rule above: it must be deliberate, narrowly scoped to a specific, approved workload decision (see the exceptions below), and never a general or standing grant. It simply is not categorized, guarded, or described as identity mutation.

### LIMS WS2025 DEV v2 — dedicated time-zone policy assignments and RBAC (Policy pilot)

"Policy assignments" and "RBAC" each always require an explicit, specific decision before implementation (see "Explicit architecture decision required" above) — neither is categorically prohibited, and assigning an already-existing Entra principal (here, a policy assignment's own newly created system-assigned identity) to an Azure role is not an Entra mutation. For the two LIMS WS2025 DEV v2 virtual machines explicitly covered by the compute-foundation exception above, that decision is: assign the Microsoft built-in Azure Policy definition "Configure time zone on Windows machines." (`6141c932-9384-44c6-a395-59e4c057d7c9`, never copied into a custom definition) individually to each of the two named VMs — resource scope only — each with its own dedicated, newly created system-assigned identity, and grant each identity the one built-in role its policy definition requires for remediation, at the narrowest scope that role's mechanics permit.

**Why this capability is a dedicated, VM-scoped composition rather than a grant of permission to the existing broader subscription-scoped `configure-windows-timezone-dev` assignment's identity (`2dea906c-2e98-4b2c-ab4b-2d002de614e7`):** supplied customer what-if evidence confirms both the v1 and v2 LIMS DEV VMs reside in the same resource group, `rg-compute-lims-dev-westeu` (this is now established fact, not an open question — see the corrected record in `docs/operations.md`). Granting that broader assignment's identity a resource-group-scope role, while manually selecting only the two v2 VMs during remediation, does **not** isolate enforcement to v2: that broader assignment's own `policyRule` already evaluates every eligible Windows VM in its subscription-wide scope, so a future applicable update to a v1 resource could still cause it to deploy a guest configuration assignment against v1, independent of any role grant decision made here. Two dedicated, VM-scoped assignments avoid this structurally: each one's own `policyRule` only ever evaluates the single VM it is scoped to, regardless of any future v1 change.

This decision covers, for this workload only, exactly:

- Two `Microsoft.Authorization/policyAssignments` resources, each individually scoped to one of the two named VMs (`vm-lims-dev-v2-westeu-001`, `vm-lims-dev-v2-westeu-002`) — never at subscription or resource-group scope — assigning built-in definition `6141c932-9384-44c6-a395-59e4c057d7c9` unmodified, with `TimeZone="(UTC+01:00) Amsterdam, Berlin, Bern, Rome, Stockholm, Vienna"` (that definition's own display-string parameter value, verified present in its `allowedValues`), `IncludeArcMachines="false"` (verified as that definition's own **string**-typed parameter, not a Bicep boolean), and `enforcementMode="Default"`.
- Each assignment declares its own dedicated **system-assigned** identity (never the existing broader assignment's identity, and never a standalone user-assigned identity).
- Two `Microsoft.Authorization/roleAssignments` resources granting **Guest Configuration Resource Contributor** (`088ab73d-1256-47ae-bea9-9de8e7131f31`) — resolved from each policy assignment's own `identity.principalId` output, never hardcoded or guessed — scoped to exactly the resource group hosting the two named v2 VMs (`rg-compute-lims-dev-westeu`), using deterministic role-assignment names and `principalType: 'ServicePrincipal'`.
- Resource-group scope for these role assignments, rather than VM scope, is the architecturally minimum viable grant for this specific policy's DeployIfNotExists mechanics: Microsoft's own "Remediate non-compliant resources" documentation confirms the nested remediation deployment executes at the resource group of the target resource by default, and the Guest Configuration Resource Contributor role's own action list already includes `Microsoft.Resources/deployments/*` alongside the guest-configuration-assignment actions — so no second role is required, only this scope. **This RBAC grant's scope is the resource group, not a VM — it is the *policy assignments* above, not this role grant, that are restricted to the two named VMs; this distinction must not be blurred when describing this capability.** See `docs/operations.md` for the full verification.

This does **not** authorize: creating, modifying, deleting, or excluding resources from the existing subscription-scoped `configure-windows-timezone-dev` policy assignment, its parameters, or its identity — that assignment is left completely unchanged and continues to overlap with the two VM-scoped assignments above until a separate, future consolidation decision after cutover (see `docs/operations.md`); granting any permission to that existing assignment's identity (`2dea906c-2e98-4b2c-ab4b-2d002de614e7`); creating any `Microsoft.GuestConfiguration/guestConfigurationAssignments` resource directly; creating any custom policy or role definition; creating any standalone user-assigned identity; subscription-wide Owner or Contributor, or any role at subscription scope; any role beyond Guest Configuration Resource Contributor; any automatic remediation task; any change to the v1 LIMS DEV VMs or the four existing patch-policy assignments; or expansion to any other VM, workload, or environment. Expansion beyond these two VMs/assignments/role grants requires its own separate, specific decision recorded as a new exception.

### LIMS WS2025 DEV v2 — guest data-disk preparation (opt-in, disabled by default)

Guest-level disk initialization/formatting is not default repository authority — it is a guest OS mutation, not Azure resource infrastructure, and falls outside the normal "Explicit architecture decision required" list above only because that list enumerates Azure Resource Manager-level capabilities, not guest-OS actions; it is treated with at least the same level of deliberateness. For the two LIMS WS2025 DEV v2 virtual machines explicitly covered by the compute-foundation exception above, that decision is: deliver one Microsoft-documented, reviewable PowerShell script via `Microsoft.Compute/virtualMachines/runCommands`, scoped individually to each of the two named VMs, that may initialize, partition, format, and label **only** the specific, named, pre-approved data disk(s) on that VM, strictly behind an explicit opt-in parameter that defaults to disabled, plus an explicit per-VM Validate/Apply execution selector that also defaults to performing nothing.

This exception covers, for this workload only, exactly:

- Two `Microsoft.Compute/virtualMachines/runCommands` resources (API version `2024-11-01`), each a child of exactly one of the two named VMs (`vm-lims-dev-v2-westeu-001`, `vm-lims-dev-v2-westeu-002`) — never a subscription/resource-group-scoped Run Command, never targeting any other VM, and never created unless the module's `enableGuestDiskPreparation` parameter is explicitly set to `true` (default `false`) **and** that VM is selected by `guestDiskPreparationExecutionTarget` (`None` | `ValidateApp` | `ValidateSql` | `ValidateBoth` | `ApplyApp` | `ApplySql`, default `None`). There is deliberately no `ApplyBoth` value — applying to both VMs in a single deployment is structurally impossible, not merely discouraged by convention.
- A fully inline script (`source.script`, no storage account, no public URL, no secret) that runs in one of two modes, `Validate` or `Apply`. `Validate` is fully read-only — every mutating function is unreachable from that code path by construction — and reports the guest's current state and the action it would take. `Apply` always rebuilds and re-runs every check fresh (fixed allowlist, identity, disk mapping, stable disk identity, existing layout, destination-letter occupancy) immediately before mutating; a prior report, including one from an earlier run of this same script, is never trusted as authorization.
- Independent, duplicated verification: the script carries its own fixed, hardcoded allowlist of the exact approved subscription/resource group/VM/computer name and disk descriptors below. Caller-supplied parameters and the Azure Instance Metadata Service (IMDS) are each checked separately against that fixed allowlist — never only against each other — so a caller/IMDS pair that is internally self-consistent but points at the wrong VM, subscription, resource group, or disk still fails closed.
- Exactly these disk targets, identified by managed-disk resource name and Azure LUN (never by disk number, ordinal position, size alone, or "all RAW disks"), after excluding the OS disk by its actual reported `IsBoot`/`IsSystem` role and excluding the Azure temporary/resource disk by positive cross-reference against the Instance Metadata Service's own authoritative `compute.storageProfile.resourceDisk.size` value (never a hardcoded disk number, SCSI port, or controller co-location assumption; a missing/unreadable IMDS value fails the run closed rather than guessing):
  - APP (`vm-lims-dev-v2-westeu-001`): LUN 0, the existing `appDataDiskName` managed disk (128 GiB) — destination `A:`, NTFS, 4 KiB allocation unit, label `LIMS-App`.
  - SQL (`vm-lims-dev-v2-westeu-002`): LUN 0, the existing `sqlDataDiskName` managed disk (1024 GiB) — destination `E:`, NTFS, 64 KiB allocation unit, label `SQL-Data`; LUN 1, the existing `sqlLogDiskName` managed disk (512 GiB) — destination `F:`, NTFS, 64 KiB allocation unit, label `SQL-Logs`.
- On the SQL VM only, a conditional, narrowly defined move of the empty virtual DVD-ROM drive letter from `E:` to `Z:`, performed before SQL DATA's partition is created at `E:` — only performed if `E:` is independently, positively confirmed (via `Win32_CDROMDrive`) to be the single expected `Microsoft Virtual DVD-ROM` device with no media loaded, and `Z:` is confirmed free (across the optical-device inventory, the DVD volume inventory, the ordinary volume inventory, and the partition inventory), and the move's success is independently re-confirmed afterward; any missing, unexpected, or ambiguous device identity, any loaded or unknown media state, or an occupied destination stops the entire VM's run (no mutation of any kind, on either SQL disk) instead. The APP VM's DVD-ROM letter is never touched.

This does **not** authorize: selecting or mutating any disk by size, ordinal number, drive-letter guess, tag, or "all RAW disks" discovery; touching the OS disk, the Azure temporary disk, `C:`, `D:`, any v1 LIMS DEV resource, or any disk/VM not explicitly named above; `Clear-Disk`, `diskpart clean`, partition deletion, storage pools, or any blanket disk-state operation; repairing, reformatting, or auto-resuming an already-initialized disk that does not exactly match the intended layout (the script fails closed and stops for manual review instead); retrying a failed format automatically; weakening the Azure Instance Metadata Service identity/LUN/resource-name/capacity verification described in `docs/operations.md` to make execution succeed — if that verification cannot establish an unambiguous mapping, the correct outcome is a failed run, never a broader match; or expansion to any other VM, workload, or environment. Expansion beyond these two VMs/disks requires its own separate, specific decision recorded as a new exception.

### LIMS WS2025 DEV v2 — SQL installation-media staging on the SQL VM

The RBAC exception above grants the SQL v2 VM's (`vm-lims-dev-v2-westeu-002`) own existing system-assigned identity Storage Blob Data Reader on the `mssql-2022-source` container, but by itself authorizes no actual use of that access. This exception is the separate, explicit decision that authorizes using it: a guest-context PowerShell script running as that VM's own identity may list the container's blobs and download their contents, writing them only under `C:\SQLMedia\SQL2022` on that VM's own local disk, so the approved SQL Server 2022 installation media is staged and available for a human operator to run SQL Server Setup manually later. This is guest-level execution — explicitly narrower than, and not a reopening of, the general "no guest-level execution" posture elsewhere in this document; it is authorized only for this one script, this one VM, this one source container, and this one destination path.

This exception covers, for this workload only, exactly:

- Enumerating (listing) the full contents of the existing `mssql-2022-source` container and downloading blob contents from it, authenticating only via the SQL VM's own existing system-assigned managed identity (the same identity, same OAuth2 bearer token flow, already covered by the "Managed identity exception (system-assigned only)" and the RBAC exception above) — never an account key, connection string, or SAS token.

- Rerunning the same script safely and repeatedly: a file whose existing length already matches the source is left untouched (skipped), and only a missing or length-mismatched file is (re)downloaded, written first to a temporary file beside its destination, verified, then moved into place — never a partial/resumed byte range.

Expansion beyond this one script/VM/container/destination requires its own separate, specific decision recorded as a new exception.

### LIMS WS2025 DEV v2 — SQL Server 2022 Enterprise Database Engine installation on the SQL VM

Guest-level SQL Server Setup execution, and the Azure control-plane registration that follows a successful install, are each not default repository authority — installing/configuring SQL Server is explicitly called out as unauthorized by every exception above this one (compute foundation, patch-onboarding, and the two media-staging/RBAC exceptions immediately above). For the existing LIMS WS2025 DEV v2 SQL virtual machine (`vm-lims-dev-v2-westeu-002`) explicitly covered by the compute-foundation exception above, and using only the media already staged under the narrow staging exception immediately above, that decision is: a guest-context PowerShell script running as SYSTEM/Administrator on that one VM may run the pinned, signed `C:\SQLMedia\SQL2022\SETUP.EXE` once to perform one unattended installation of the SQL Server 2022 Database Engine only (default `MSSQLSERVER` instance) with the exact configuration below, followed by one Azure CLI step — run from the pipeline, not the guest, since the guest's own managed identity has no `Microsoft.SqlVirtualMachine` write permission — that registers the already-installed instance with the SQL Server IaaS Agent extension in **LightWeight** management mode with Azure Hybrid Benefit licensing.

This exception covers, for this workload only, exactly:

- Exactly one guest-context execution of `C:\SQLMedia\SQL2022\SETUP.EXE` (the same pinned path verified by the staging exception's own final check) on `vm-lims-dev-v2-westeu-002` only, `/ACTION=Install`, `/FEATURES=SQL` (Database Engine, replication, and full-text only — no Analysis Services, Reporting Services, Integration Services, or Tools component), `/INSTANCENAME=MSSQLSERVER` (default instance only — no named instance, no multi-instance, no failover clustering), `/SQLCOLLATION=SQL_Latin1_General_CP1_CI_AS`, `/SECURITYMODE=SQL` (mixed mode) with the sa password supplied only via a Managed Run Command protected parameter (never a plain parameter, pipeline variable log, script file, or the auto-generated `ConfigurationFile.ini`), `/SQLSVCACCOUNT="NT SERVICE\MSSQLSERVER"` and `/AGTSVCACCOUNT="NT SERVICE\SQLSERVERAGENT"` (the documented default virtual accounts — "the agreed default service-account model"; no domain or custom service account of any kind), `/AGTSVCSTARTUPTYPE=Disabled` (SQL Server Agent installed but not started), `/TCPENABLED=1` with the Database Engine explicitly configured (and verified, after a service restart) to listen on static TCP port 1433 only, `/SQLSYSADMINACCOUNTS` populated only from an explicit, caller-supplied list of approved Windows principals (never a hardcoded or guessed value), `/INSTALLSQLDATADIR`/`/SQLUSERDBDIR` under the existing `E:` SQL DATA volume, `/SQLUSERDBLOGDIR` under the existing `F:` SQL LOG volume, and `/SQLTEMPDBDIR`/`/SQLTEMPDBLOGDIR` under the existing `D:` Azure temporary volume — all four paths, plus every `/SQLTEMPDBFILECOUNT`/`/SQLTEMPDBFILESIZE`/`/SQLTEMPDBFILEGROWTH`/`/SQLTEMPDBLOGFILESIZE`/`/SQLTEMPDBLOGFILEGROWTH` TempDB sizing value, supplied only as explicit caller inputs, never hardcoded — and `/UPDATEENABLED=False` (Setup's own update-discovery stays off; servicing is handled exclusively through the existing Azure Update Manager patch-onboarding pilot above).
- Before Setup is ever launched: independent re-verification of the exact same fixed target identity (subscription/resource group/VM name/computer name) used by the staging and guest-disk-preparation scripts above; Authenticode signature verification of `C:\SQLMedia\SQL2022\SETUP.EXE` (valid, Microsoft-signed) immediately before execution; and confirmation that `E:`/`F:` carry the volume labels (`SQL-Data`/`SQL-Logs`) set by the guest data-disk preparation exception above and that `D:` exists and is writable — a label mismatch or missing volume stops the run before Setup is launched.
- Rerun safety: if the `MSSQLSERVER` service already exists, this script validates its state (service status, edition, collation, TempDB location) against the expected configuration and either reports an already-satisfied idempotent success (service healthy and matching) or stops with a clear diagnostic (service present but partial/unexpected state) — it never attempts an automatic repair, uninstall, or reinstall over an existing instance.
- After a successful install (Setup exit code `0`, or `3010` reported as "succeeded, reboot required" and the run stopped there for a human to reboot and rerun — never treated as a hard failure, and never proceeding to post-install verification against a possibly-not-yet-functional instance), capturing and reporting: the exit code, reboot-required status, resulting edition, `SERVERPROPERTY('ProductVersion')`, collation, and `MSSQLSERVER`/`SQLSERVERAGENT` service states — never the sa password, never the full Setup command line, and never a raw Setup log.
- A reviewable mitigation for the known risk that `D:` is the Azure temporary/ephemeral disk and is recreated empty on VM deallocation/reallocation: the Database Engine service's own Windows startup type is set to **Manual** (`SQLSERVERAGENT` stays **Disabled**), and a single Windows Scheduled Task (`LIMS-SQL-TempDb-PrepareAndStart`, triggered `AtStartup`, running as SYSTEM) is the only thing that ever starts the engine after a reboot — SQL still starts automatically at boot, through that task, not through the SCM. That task's script waits for `D:` to become available, creates the configured TempDB directory if missing, grants the `MSSQLSERVER` service account the required ACL via `icacls.exe` (checking its exit code and refusing to proceed on failure), and **only then** starts `MSSQLSERVER` — an explicit sequence, never a delayed-auto-start timing assumption. The install and rerun paths never recursively delete the TempDB directory. A true end-to-end check of this sequence (after a real reboot, and separately after a real Azure temporary-disk recreation) is a documented, DEV-only, operator-performed procedure in `docs/operations.md`, not an in-run destructive test.
- Disabling the `sa` login only from a Windows-authenticated session whose own connected identity (`SYSTEM_USER`) exactly matches one of the explicitly approved Windows SQL administrator principals **and** has sysadmin membership (`IS_SRVROLEMEMBER('sysadmin')`). Sysadmin membership of the Managed Run Command automation identity (SYSTEM) is deliberately insufficient and never authorizes the disable. Because Managed Run Command always connects as SYSTEM, the guest script is expected to report this step as `PendingManualOperatorVerification` on every real pipeline run; the documented operator-sign-in procedure in `docs/operations.md` is what actually verifies identity and role, disables `sa`, and confirms `is_disabled = 1`. The sa password, once supplied to Setup as a protected parameter, is never used again by this script (or by that operator procedure) to connect to the instance.
- Exactly one post-install Azure CLI step, run from the pipeline (not the guest), registering `vm-lims-dev-v2-westeu-002` with the SQL Server IaaS Agent extension in `LightWeight` management mode (`az sql vm create --sql-mgmt-type LightWeight`) with `--license-type AHUB` (Azure Hybrid Benefit) — `LightWeight` is the only mode valid for a self-installed SQL Server 2022 VM (`NoAgent` applies only to SQL Server 2008/2008 R2) and deliberately does not deploy the IaaS extension's own automated-patching or automated-backup features, since servicing continues to be handled exclusively through the existing Azure Update Manager patch-onboarding pilot above, not through this extension.
- Documentation of the SQL v2 patching handoff (see `docs/operations.md`): confirming the VM's configured update source offers SQL Server updates, triggering an Update Manager assessment, confirming the existing `mc-lims-nonprod-westeu` maintenance schedule includes the Updates classification, and recording `SERVERPROPERTY('ProductVersion')` after the first patch cycle for comparison against the intended servicing build before the first database restore — a documented runbook step, not a new deployable resource.

This does **not** authorize: any SQL Server feature beyond the Database Engine (Analysis Services, Reporting Services, Integration Services, Tools, Full-Text is installed only as an inherent part of the `SQL` feature bundle itself, never separately configured); a named instance, multiple instances, or any failover-clustering/Always On configuration; any service account other than the two named default virtual accounts; enabling SQL Server Agent to actually run (only installed, disabled); any network protocol or port other than TCP/IP on port 1433; any `/SQLSYSADMINACCOUNTS` value invented, guessed, or defaulted by this repository (the caller must always supply the approved list); any change to the staged media, the staging script, or the staging exception above; any SQL IaaS management mode other than `LightWeight`; any automated-patching or automated-backup feature of the SQL IaaS extension; any change to the VM's own compute/disk/network/identity configuration; any Windows Update/Microsoft Update source configuration change (verifying the existing configuration is covered; changing it is not); any uninstall, repair, upgrade, or version change of an existing instance; execution against the APP VM (`vm-lims-dev-v2-westeu-001`) or any other VM; or expansion to any other VM, workload, instance, or environment. Expansion beyond this one script/VM/instance requires its own separate, specific decision recorded as a new exception.

### LIMS APP data-disk content migration (DEV first; mapping-driven)

Application content migration is not default repository authority — the compute-foundation exception above explicitly does not authorize it, and the guest data-disk preparation exception authorizes initializing APP v2 `A:` only, never copying v1 content onto it. For the existing LIMS replacement APP virtual machine (`vm-lims-dev-v2-westeu-001`) covered by the compute-foundation exception, that decision is: a reusable, mapping-driven Azure DevOps workflow may copy the existing APP data-disk contents onto the already-prepared destination `A:` volume, starting with DEV as the only enabled environment.

This exception covers, for this workload only, exactly:

- One reviewed environment mapping (`operations/compute/lims-app-data-disk-migration/LimsAppDataDiskMigration.Mapping.ps1`) listing exactly the supported environments `dev`, `tst`, `acc`, `preprd`, and `prd`. Only an environment with `Enabled = true` may run. DEV is the only enabled row; the other four are present with the same schema so they can be onboarded by filling reviewed values and flipping `Enabled` — never by copying the pipeline or scripts.
- For DEV, independently verifying both mappings before any copy: source VM `vm-lims-dev-westeu-001`, data disk `vmlimsdevwesteu001-v2-datadisk` at LUN 1; destination the existing `A:` volume (label `LIMS-App`) on `vm-lims-dev-v2-westeu-001` / computer `lims-dev-v2-001`, data disk `appdata-vm-lims-dev-v2-westeu-001` at LUN 0, attested guest UniqueId `60022480D1B07E6ACD98417F86591F4B`. Plan and stage fail closed if any live identity, attachment, region, or Disk Encryption Set check differs from that mapping (including a missing DES resource-ID pin). Azure managed-disk identity (resource ID, attachment, LUN, DES, ARM uniqueId) is separate from Windows guest-disk identity. Guest copy binds `A:` by the independently attested Windows UniqueId plus Azure resource ID, LUN, and partition. ARM uniqueId is not Windows UniqueId and is not used as guest identity. The snapshot-derived disk has no reviewed guest UniqueId until inspect evidence is reviewed; if that correlation remains unproven, print the inventory and stop before disk-state changes or copying. A matching `A:` label, drive letter, Windows disk number, LUN, or IMDS `resourceDisk.size` alone is insufficient. IMDS `resourceDisk.size` is not used to exclude Azure temporary storage: on DEV that value does not match the Windows temporary disk, and SCSI LUN 1 collides with Azure temporary storage.
- Separate manual pipeline actions `plan` (default, read-only), `attach-and-inspect`, `stage`, and `cleanup` in one pipeline (`.azuredevops/pipelines/migrate-lims-app-data-disk.yml`), reusing the existing Azure DevOps service connection and the existing Managed Run Command submit/wait/cleanup helpers. `migrationRunId` defaults to the literal token `auto`, resolved to this `Build.BuildId` for `stage` and `attach-and-inspect` before numeric validation; `cleanup` rejects `auto` and requires the original run's numeric ID. The resolved value is passed through the task environment, never interpolated as free text into Bash or PowerShell source. `azureFilesUnc` defaults to `not-used` for actions that ignore UNC; `configure-app` and `activate-app` reject that placeholder.
- `attach-and-inspect` only: the same Azure snapshot/attach path as `stage` (operator-recorded `online` or `writes-quiesced`, incremental snapshot of only the mapped source disk, temporary disk from that snapshot using the verified Disk Encryption Set, attach only to APP v2 at the mapped unused LUN) without requiring the stage/cleanup reparse gates. The per-environment lock is an If-Match update of the destination VM lock tags, acquired before any snapshot, disk create, or attach; Microsoft.Compute/disks create-or-update is not exclusive and is not the lock. Guest inspection on APP v2 is read-only: print the snapshot-derived disk Azure ID, LUN, and ARM uniqueId beside the Windows inventory, require `A:` = `60022480D1B07E6ACD98417F86591F4B`, leave the disk attached, and stop. ARM uniqueId is Azure evidence, not a Windows UniqueId. Snapshot guest binding remains unproven until reviewed. No `Set-Disk`, drive-letter change, initialize, format, Robocopy, or Azure Files access. Overlapping migration attempts, including retries with the same run ID, are refused. The inspect Run Command is preserved until temporary-disk cleanup succeeds. After attach, destination VM tags record `Prepared` and the exact token `limsAppMigGuestSubmitted=false`. Submit and pre-submit recovery are mutually exclusive If-Match transitions (`Prepared → Submitting` vs `Prepared → Recovering`); only the winning path may continue. Missing, empty, or any value other than the exact token `false` is unknown and blocks both paths. Failure after attach and before guest submission is recovered only through reviewed `preSubmitRecovery` when the attempt is still `Prepared`, guest submission is the explicit token `false`, the command is NotFound, and this run holds the lock; Run Command `NotFound` alone is indeterminate. Snapshot retain is the default.
- `stage` only: an incremental snapshot of the mapped source disk during an operator-recorded capture window (`online` or `writes-quiesced`), a temporary managed disk created from that snapshot using the verified Disk Encryption Set, attached only to APP v2 at the mapped unused LUN. The destination-VM If-Match lock is held across attach-and-inspect, stage, guest command submission/execution, and cleanup. Overlapping migration attempts are refused even with the same migration run ID; that ID remains the ownership key for cleanup and recovery. Destination VM tags record status only. `stage` and `cleanup` stay blocked until both Windows reparse validations are `Passed`, except reviewed attach-and-inspect pre-submit recovery.
- Guest copy on APP v2 via Managed Run Command: dump a read-only guest disk inventory, then identify `A:` by attested Windows UniqueId plus Azure resource ID, LUN, and partition. Do not treat ARM uniqueId as Windows UniqueId. The snapshot-derived disk requires a reviewed guest UniqueId; if correlation remains unproven, print the inventory and stop before `Set-Disk` or copy. Present the snapshot volume under an unused drive letter, and fail if Windows would require `Initialize-Disk` or `Format-Volume`. Revalidate identity before changing disk state or drive letters and again before copying. Both copy roots must be local volumes. Robocopy preview, destination capacity check, copy of data/attributes/timestamps (`/COPY:DAT`, `/DCOPY:DAT`) including `temp` and other local application content, explicit exclusion of `lv89\sdmshome` without traversing or recreating it, never following reparse points (`/XJ`). Unexpected source reparse points and any destination reparse point in a writable path fail before preview and before copy. Full Robocopy log on APP v2, compact pipeline summary, exit-code interpretation, and a second comparison that fails on copy errors or unexplained differences. v2 service permissions are not applied here.
- `cleanup` only: after the guest command is Found and terminal (`Succeeded`, `Failed`, or `Canceled`), detach and delete only the temporary disk created by the selected run, after proving run ownership, exact resource and attachment IDs, and the temporary-disk → snapshot → original-source lineage. A Run Command `NotFound` response is indeterminate and does not prove the command was never submitted (the window after disk attach and before the command resource exists). Authorization, network, and other lookup failures are not treated as resource-not-found. Snapshot deletion is an explicit retention decision (default retain) and still requires those IDs. Name-only deletion is refused. The original source disk and destination `A:` are never detached or deleted. APP v2 services are left stopped pending review of JDBC, UNC, Apache, and Shibboleth settings. SQL VMs and the live DEV Azure Files share are out of scope.

This does **not** authorize: initializing or formatting any volume; copying onto any volume other than the mapped destination `A:`; following reparse points into external storage; copying `lv89\sdmshome`; copying ACLs or applying v2 service permissions (see the post-copy configuration exception below); starting APP v2 services; mutating the source v1 VM or its original data disk; deleting an incremental snapshot unless the operator explicitly opts in; targeting SQL v2 or any other VM; or running against `tst`, `acc`, `preprd`, or `prd` until that environment's mapping row is reviewed and enabled. Expansion to another environment is a mapping change plus a recorded onboarding review, not a new pipeline.

### LIMS APP v2 post-copy configuration (DEV first; mapping-driven)

After the mapped `A:` copy is proven complete, a reusable, mapping-driven Azure DevOps workflow may register the replacement APP v2 local account, Windows services, and Azure Files startup task on `vm-lims-dev-v2-westeu-001` only. This is not default repository authority and does not reopen stage/cleanup.

This exception covers, for this workload only, exactly:

- The same reviewed environment mapping used by the content-migration exception. DEV is the only enabled environment. Stage and cleanup remain gated by `WindowsReparseValidationStatus` and `WindowsSymlinkValidationStatus`.
- Manual pipeline actions `configure-app` and `activate-app` in `.azuredevops/pipelines/migrate-lims-app-data-disk.yml`, submitted only to the mapped destination APP v2 VM through the existing Managed Run Command helpers. Legacy APP and both SQL VMs stay outside all write and guest-command paths.

## Prohibited

No deployable functionality for:

- Entra ID users or groups
- Application registrations or enterprise applications
- Service principals
- Directory roles
- Microsoft Graph mutations
- Identity lifecycle management
- Creation or modification of managed identities (narrow exception: see "Managed identity exception (system-assigned only)" above)

RBAC assignment is deliberately not listed here: assigning an already-existing Entra principal to an Azure role is not an Entra ID mutation (see "RBAC and Entra ID mutation are distinct" above). RBAC still requires its own explicit, specific, approved decision per the "Explicit architecture decision required" section — it is simply categorized correctly rather than guarded as identity mutation.

The deployment identity used by this repository is intentionally granted no Entra ID permissions. Lack of identity permission is never treated as a defect to work around, and permissions are not broadened to compensate. Existing Azure resources and identities may be referenced read-only where necessary, but this repository does not create or modify identity — that remains unconditional. The managed-identity exception above is the only departure from this section, and only for the specific workload(s) it names.

This repository also does not introduce Terraform-style state (state files, state storage accounts, deployment-state databases, state locking, or custom deployment inventory databases), and does not use Azure Deployment Stacks purely to introduce resource-ownership/state tracking.
